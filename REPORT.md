## 1. Мета роботи

Мета лабораторної роботи — удосконалити наскрізний Java-проєкт «Кінотеатр», реалізувавши параметризоване сховище даних, власний виняток із збереженням першопричини, анотацію для опису CSV-стовпців та універсальний механізм експорту на основі Reflection API.

Додатково необхідно забезпечити імпорт CSV, перевірити можливість відновлення початкових об'єктів після експорту, виконати автоматизоване тестування та зберегти сумісність із попередніми лабораторними роботами.

## 5. Параметризоване сховище Repository<T>

Клас Repository<T> реалізує типобезпечне сховище об'єктів.

Параметр T задає тип записів під час створення сховища, тому компілятор перевіряє правильність додавання об'єктів.

Основні методи:

- add(T item) — додає запис.
- all() — повертає незмінний знімок записів.
- find(Predicate<? super T> condition) — виконує пошук за умовою.

Пошук реалізовано за допомогою Stream API.

Повернення незмінного знімка запобігає зміні внутрішнього стану сховища через отриману колекцію.

## 6. Предметна модель ScreeningRecord

Для лабораторної №5 створено модель ScreeningRecord.

Основні поля:

| Поле Java | Тип | CSV-заголовок |
|---|---|---|
| film | String | фільм |
| hall | String | зал |
| startAt | LocalDateTime | час |
| ticketPrice | double | ціна |
| soldTickets | int | продано |

Бізнес-ключ запису визначається назвою фільму та часом початку: film + startAt.

Для предметної моделі передбачено перевірку коректності вхідних значень.

## 7. Анотація @CsvColumn

Власна анотація @CsvColumn описує назву стовпця для поля класу.

@Retention(RetentionPolicy.RUNTIME) забезпечує доступність анотації під час виконання програми.

@Target(ElementType.FIELD) дозволяє застосовувати її до полів.

Анотація не виконує експорт самостійно: її метадані зчитує CsvExporter за допомогою Reflection API.

## 8. Універсальний CSV-експортер

CsvExporter отримує клас записів, шлях до файлу та список об'єктів.

Алгоритм роботи:

1. Отримання полів, позначених @CsvColumn.
2. Сортування полів за їхніми Java-іменами.
3. Формування заголовка CSV.
4. Отримання значень полів через рефлексію.
5. Перетворення значень у текст.
6. Екранування спеціальних символів.
7. Запис файлу в UTF-8.

Для ScreeningRecord формується заголовок:

`фільм,зал,продано,час,ціна`

Порядок полів є детермінованим і не залежить від випадкового порядку отримання метаданих.

## 9. Екранування CSV

Для коректного CSV недостатньо просто об'єднати значення комами.

Якщо значення містить кому, подвійні лапки або перенесення рядка, воно береться у подвійні лапки.

Подвійні лапки всередині значення подвоюються.

Наприклад, значення:

`Фільм "А", частина 2`

у CSV записується як:

`"Фільм ""А"", частина 2"`

Такий підхід забезпечує коректне зчитування складних текстових значень.

## 10. CSV-імпорт і round-trip

CsvParser виконує розбір CSV із підтримкою:

- значень у подвійних лапках;
- ком усередині значень;
- подвоєних лапок;
- багаторядкових полів;
- закінчень рядків LF і CRLF.

ScreeningCsvImporter перетворює CSV-рядки на ScreeningRecord і перевіряє структуру даних.

Тест round-trip виконує послідовність:

Початкові об'єкти → CSV-файл → імпорт → відновлені об'єкти.

Після імпорту перевіряється рівність початкових і відновлених записів.

Це підтверджує, що під час запису й читання не втрачаються дані, які входять до перевірюваної моделі.

## 11. Власний виняток DataStorageException

DataStorageException використовується для повідомлення про помилки зберігання та обробки даних.

Виняток дозволяє передати зрозуміле повідомлення й зберегти початкову причину помилки через cause.

Це важливо для діагностики проблем файлової системи, некоректного CSV та помилок доступу до полів.

Програма не повинна приховувати винятки порожніми блоками catch.

## 12. Додаткове завдання: JSON-експорт

Реалізовано інтерфейс Exporter<T>, який визначає спільну операцію експорту.

JsonExporter<T> реалізує цей інтерфейс і формує JSON-масив об'єктів.

Назви JSON-властивостей визначаються анотацією @CsvColumn.

Під час формування JSON враховуються типи значень: числові та логічні значення записуються без текстових лапок, рядкові значення екрануються.

Для порожнього набору формується порожній JSON-масив.

## 13. Додаткове завдання: кешування Reflection

Для зменшення повторних витрат на пошук анотованих полів створено ReflectionFieldCache.

Кеш побудовано на ConcurrentHashMap і пов'язує клас із підготовленим списком полів.

Після першого аналізу класу наступні звернення можуть використовувати вже знайдені метадані.

Для перевірки ефективності створено ReflectionBenchmark.

## 16. Відповіді на контрольні питання

### 1. Яку проблему розв'язує параметр типу в Repository<T>?

Параметр типу забезпечує типобезпечність сховища. Він дозволяє використовувати один клас для різних типів об'єктів і виявляти несумісні типи під час компіляції.

### 2. Чим параметризований клас відрізняється від raw type?

Параметризований клас використовує конкретний аргумент типу, наприклад Repository<ScreeningRecord>. Raw type — Repository без аргументу типу — послаблює перевірки компілятора та може призводити до помилок приведення типів.

### 3. Навіщо Predicate<? super T> у методі пошуку?

Такий запис дозволяє передавати предикат, який приймає об'єкти типу T або його супертипу. Це робить API гнучкішим без втрати типобезпечності.

### 4. Чому all() має повертати незмінний знімок?

Щоб зовнішній код не міг змінити внутрішню колекцію сховища. Знімок також відокремлює отриманий результат від подальших змін Repository.

### 5. Що таке checked exception і коли він доречний у цій роботі?

Checked exception — виняток, який компілятор вимагає обробити або оголосити через throws. Прикладом є IOException під час файлових операцій. Він доречний там, де викликач повинен явно враховувати можливість збою вводу-виводу.

### 6. Для чого зберігати cause власного винятку?

Cause зберігає початковий виняток, який спричинив помилку вищого рівня. Це дозволяє побачити першопричину проблеми та спрощує налагодження.

### 7. Чим Path і Files кращі за складання шляху рядком?

Path представляє шлях як спеціалізований об'єкт, а Files надає стандартні файлові операції. Це зменшує залежність від роздільників шляхів конкретної операційної системи та робить код зрозумілішим.

### 8. Чому кодування потрібно задавати і під час запису, і під час читання?

Якщо використовувати різні кодування, символи можуть бути пошкоджені. Явне UTF-8 під час обох операцій забезпечує однакове представлення тексту.

### 9. Що роблять @Retention(RUNTIME) і @Target(FIELD)?

@Retention(RUNTIME) зберігає анотацію доступною під час виконання програми. @Target(FIELD) обмежує її використання полями класів.

### 10. Чому анотація не виконує експорт сама?

Анотація є лише метаданими. Логіку експорту реалізує програмний код, який знаходить анотацію через рефлексію та використовує її значення.

### 11. Чим getDeclaredFields() відрізняється від отримання публічних полів?

getDeclaredFields() повертає поля, оголошені безпосередньо в класі, незалежно від модифікатора доступу, але без успадкованих полів. getFields() повертає доступні публічні поля, включно з успадкованими.

### 12. Навіщо перевіряти trySetAccessible()?

Метод намагається дозволити рефлексивний доступ до поля й повертає результат операції. Перевірка потрібна, оскільки доступ може бути обмежений правилами модулів або безпеки.

### 13. Чому порядок полів для CSV потрібно зробити детермінованим?

Щоб однакові дані завжди формували однакову структуру файлу. Це спрощує імпорт, тестування, порівняння файлів і відтворюваність результатів.

### 14. Чому split(",") не підходить для загального CSV?

Тому що кома може бути частиною значення в лапках, а саме значення може містити лапки й перенесення рядків. Звичайний split не враховує правил CSV.

### 15. Як екрануються кома, лапка й перенесення рядка в CSV?

Значення зі спеціальними символами береться у подвійні лапки. Кожна подвійна лапка всередині значення замінюється двома подвійними лапками.

### 16. Чому порожній список потребує окремого параметра Class<T>?

Через стирання типів у Java під час виконання та відсутність елементів, за якими можна визначити клас. Class<T> надає експортеру інформацію про поля навіть для порожнього списку.

### 17. Чим універсальний експортер відрізняється від предметного fromCsv?

Універсальний експортер працює з різними класами за допомогою анотацій і рефлексії. Предметний fromCsv знає конкретну структуру та правила створення об'єкта певної моделі.

### 18. Які рівні помилок розрізняє програма?

Можна виділити помилки аргументів і предметних значень, помилки структури CSV, помилки доступу до полів через рефлексію та помилки файлової системи. Вони обробляються на відповідних рівнях із збереженням діагностичної інформації.

### 19. Що доводить тест round-trip?

Він перевіряє, що після експорту та повторного імпорту відновлені об'єкти еквівалентні початковим за полями, які повинні зберігатися у файлі.

### 20. Чому виняток не можна поглинати порожнім catch?

Тому що програма приховає збій і може продовжити роботу з неправильними або неповними даними. Помилку потрібно обробити змістовно, передати вище або загорнути з поясненням і збереженням cause.

## 17. Висновок

У ході лабораторної роботи №5 було продовжено розробку Java-застосунку «Кінотеатр» та реалізовано механізми типобезпечного зберігання й універсального експорту даних.

Створено параметризоване сховище Repository<T>, яке дозволяє додавати об'єкти, отримувати незмінні знімки колекції та виконувати пошук за предикатом. Використання generics допомогло відокремити логіку зберігання від конкретної предметної моделі.

Особливу увагу приділено роботі з файлами та метаданими класів. За допомогою анотації @CsvColumn і Reflection API реалізовано універсальний CSV-експортер, який не потребує окремого алгоритму для кожного нового класу. CSV-парсер та імпортер забезпечують відновлення записів, а тести round-trip перевіряють збереження даних після повного циклу запису й читання.

Для обробки помилок застосовано DataStorageException із можливістю збереження першопричини. Це покращує діагностику проблем і робить поведінку програми зрозумілішою.

Крім обов'язкових завдань, реалізовано три додаткові можливості: JSON-експорт через спільний інтерфейс, кешування метаданих рефлексії та підтримку успадкованих анотованих полів. Локальний бенчмарк продемонстрував прискорення пошуку метаданих приблизно у 25,54 раза в умовах проведеного вимірювання.

Коректність реалізації підтверджено запуском 122 автоматизованих тестів без помилок і пропусків. Статичний аналіз SpotBugs не виявив дефектів.

Таким чином, поставлені завдання виконано. Отримано практичний досвід використання generics, анотацій, Reflection API, файлового вводу-виводу, власних винятків, тестування та оптимізації Java-застосунків. Проєкт зберіг функціональність попередніх лабораторних робіт і став більш універсальним, придатним до розширення та супроводу.
## 18. Автоматичне версіонування Maven

Єдиним джерелом версії застосунку є pom.xml (5.0.0). Maven записує версію до JAR-маніфесту як Implementation-Version. Клас CinemaController отримує її через getImplementationVersion(), тому --version і --help не містять жорстко заданої версії.

Виправлення виконано у Pull Request #37: https://github.com/ViSPry/LAB_KZP/pull/37. Усі 6 перевірок GitHub Actions завершилися успішно.
