# 8. Базовий тип Screening

У ЛР №2 `Screening` представляв одну конкретну сутність.

У ЛР №3 його перетворено на абстрактний базовий клас для декількох видів кіносеансів.

Клас оголошено як:

`public abstract sealed class Screening permits RegularScreening, PremiumScreening`

Спільні поля:

- `film`;
- `hall`;
- `ticketPrice`;
- `sold`;
- `durationMin`.

Поля залишаються `private final`.

Таким чином, спільний стан та правила предметної області не дублюються у кожному підтипі.

---

# 9. Чому використано абстрактний клас

Для моделі було обрано абстрактний клас, оскільки різні види кіносеансів мають спільний стан.

І `RegularScreening`, і `PremiumScreening` мають:

- назву фільму;
- номер залу;
- ціну квитка;
- кількість проданих квитків;
- тривалість;
- однакові базові правила валідації.

Якби використовувався лише інтерфейс, ці поля та значну частину спільної реалізації довелося б розміщувати окремо.

Абстрактний клас дозволяє одночасно визначити спільний стан і спільний контракт поведінки.

# 10. Спільні інваріанти

Для `Screening` збережено правила валідації попередньої лабораторної роботи.

| Поле | Правило |
|---|---|
| `film` | не `null` і не порожнє |

| `ticketPrice` | скінченне число та не менше 0 |
| `sold` | не менше 0 |
| `durationMin` | більше 0 |

Таким чином, перехід до спадкування не змінив набір записів, які програма вважає правильними або неправильними.

# 11. Валідація та SpotBugs

Під час реалізації абстрактного `Screening` SpotBugs виявив проблему:

`CT_CONSTRUCTOR_THROW`

Причиною було те, що конструктор базового класу міг генерувати виняток під час перевірки параметрів.

Проблему не було приховано через `@SuppressFBWarnings`.

Натомість реалізацію структурно змінено.

Публічно доступний для підтипів конструктор передає параметри до статичної перевірки, а після успішної валідації використовується внутрішній об'єкт із перевіреними значеннями.

Для цього створено приватний:

`ValidatedData record`

Таким чином, присвоєння стану відбувається лише після успішної перевірки параметрів.

Після зміни `.\mvnw.cmd clean verify` успішно проходить перевірку SpotBugs.

# 12. RegularScreening

`RegularScreening` є конкретним підтипом `Screening`.

Клас оголошено як `final`.

Він використовує спільний стан і правила валідації базового класу.

Для звичайного сеансу метод:

`revenue()`

обчислює виторг за формулою:

`ticketPrice * sold`

Метод:

`getKind()`

повертає:

`ScreeningKind.REGULAR`

---

# 13. PremiumScreening

`PremiumScreening` є другим конкретним підтипом `Screening`.

Клас також оголошено як `final`.

Крім спільного стану базового класу, він містить:

`premiumFee`

Це додаткова плата до базової ціни квитка.

Для неї перевіряється, що значення:

- є скінченним;
- не є від'ємним.

Для преміального сеансу виторг обчислюється:

`(ticketPrice + premiumFee) * sold`

Метод `getKind()` повертає:

`ScreeningKind.PREMIUM`

Отже, два підтипи мають спільний контракт, але різну реалізацію однієї операції.

# 14. ScreeningKind

Для представлення категорії кіносеансу реалізовано:

`ScreeningKind`

Enum містить два значення:

- `REGULAR`;
- `PREMIUM`.

Кожне значення має текстову назву.

`REGULAR` відповідає звичайному сеансу.

`PREMIUM` відповідає преміальному сеансу.

Enum дозволяє використовувати обмежений набір допустимих категорій замість довільних рядків.

# 15. Статичний фабричний метод fromCsv

Формат CSV попередніх лабораторних робіт збережено:

`film;hall;ticketPrice;sold;durationMin`

Метод:

`Screening.fromCsv(String line)`

розбирає рядок, перевіряє кількість полів, перетворює числові значення та створює конкретний підтип `Screening`.

Для збереження старого п'ятипольного формату використано таке правило:

- зал №1 — `PremiumScreening`;
- інші зали — `RegularScreening`.

При створенні `PremiumScreening` зі старого CSV значення `premiumFee` дорівнює `0.0`.

Це дозволяє продемонструвати роботу різних підтипів, не додаючи нового поля до CSV та не змінюючи контрольні результати попередніх лабораторних робіт.

# 16. Поліморфна операція revenue()

Головною поліморфною операцією є:

`revenue()`

Вона оголошена в базовому класі та перевизначена конкретними підтипами.

Для `RegularScreening`:

`ticketPrice * sold`

Для `PremiumScreening`:

`(ticketPrice + premiumFee) * sold`

Код, який працює зі `Screening`, не повинен визначати конкретний тип об'єкта для розрахунку виторгу.

Він просто викликає:

`screening.revenue()`

Java динамічно вибирає правильну реалізацію.

---

# 17. Гетерогенна колекція

Правильні записи зберігаються у:

`List<Screening>`

Один список може містити одночасно:

- `RegularScreening`;
- `PremiumScreening`.

Це є прикладом гетерогенної колекції.

Обробка виконується через спільний тип `Screening`, тому код статистики не залежить від конкретного підтипу.

---

# 18. Поліморфізм без if/switch за типом

Для розрахунку загального виторгу не використовується конструкція на зразок:

`if (screening instanceof RegularScreening) ...`

або центральний `switch`, який самостійно вибирає формулу.

Замість цього використовується:

`screening.revenue()`

Завдяки цьому поведінка знаходиться в самому підтипі.

Це зменшує зв'язність між кодом звітності та конкретними реалізаціями кіносеансів.

---

# 19. equals() і hashCode()

Для ієрархії `Screening` реалізовано узгоджені `equals()` і `hashCode()`.

Під час перевірки рівності враховуються:

- конкретний клас об'єкта;
- `film`;
- `hall`;
- `ticketPrice`;
- `sold`;
- `durationMin`;
- додатковий стан конкретного підтипу.

Два об'єкти різних класів не вважаються рівними навіть тоді, коли їхні базові поля однакові.

# 20. Рівність PremiumScreening

Під час початкової реалізації `equals()` і `hashCode()` було виявлено важливу проблему.

Базові поля враховувалися, але додаткове поле:

`premiumFee`

спочатку не впливало на рівність.

Це означало, що два `PremiumScreening` з однаковими базовими даними, але різною доплатою могли помилково вважатися однаковими.

Реалізацію виправлено.

До механізму рівності та формування hash-коду додано стан конкретного підтипу.

Після виправлення два преміальні сеанси з різним `premiumFee` є нерівними.

Для цього також додано окремий JUnit-тест.

# 21. HashSet

Для перевірки контракту `equals()` і `hashCode()` використовується `HashSet`.

Якщо до `HashSet` додати два рівні об'єкти `RegularScreening`, колекція повинна містити лише один логічно унікальний елемент.

Такий тест підтверджує, що реалізації `equals()` і `hashCode()` працюють узгоджено.

# 22. Sealed-ієрархія

Додатково реалізовано sealed-ієрархію.

Базовий клас оголошено:

`sealed`

і явно дозволяє:

`RegularScreening`

та:

`PremiumScreening`

через `permits`.

Це означає, що довільний сторонній клас не може успадкувати `Screening`.

Усі безпосередньо дозволені підтипи відомі компілятору.

---

# 23. Pattern matching switch

У `Main` використано pattern matching `switch` для формування текстового опису конкретного сеансу.

Оскільки базовий клас є `sealed`, Java може перевірити, що `switch` охоплює всі дозволені підтипи.

Важливо, що цей `switch` не використовується для розрахунку виторгу.

Виторг і надалі обчислюється через:

`screening.revenue()`

Тому pattern matching не дублює основну поліморфну бізнес-логіку.

# 24. Спадкування та композиція

Спадкування використано там, де виконується відношення «є різновидом».

`RegularScreening` є різновидом `Screening`.

`PremiumScreening` також є різновидом `Screening`.

Спільні поля, інваріанти та контракт поведінки природно належать базовому типу.

Для об'єктів, які не є різновидами кіносеансу, доцільніше було б використовувати композицію.

Наприклад, статистика `TicketSales` не є різновидом `Screening`, тому вона не входить до цієї ієрархії.

# 48. Контрольні питання

## 1. Яку спільну проблему розв'язує базовий тип у предметній області?

Базовий тип дозволяє винести спільні властивості та поведінку декількох схожих сутностей в одне місце. У моєму проєкті `Screening` містить дані, які однаково потрібні звичайному та преміальному сеансу. Завдяки цьому не потрібно дублювати поля та правила валідації у `RegularScreening` і `PremiumScreening`.

## 2. Чим відрізняються extends і implements?

`extends` використовується для успадкування класу від іншого класу або інтерфейсу від іншого інтерфейсу. `implements` використовується класом, який реалізує контракт інтерфейсу. У моєму проєкті `RegularScreening` і `PremiumScreening` використовують `extends Screening`, тому що `Screening` є абстрактним класом.

## 3. Навіщо базовий клас може бути abstract?

Абстрактний клас використовують, коли базовий тип описує спільну основу, але створення об'єкта цього загального типу без конкретного різновиду не має достатнього змісту. У моєму випадку створюється або `RegularScreening`, або `PremiumScreening`, а сам `Screening` визначає спільний контракт.

## 4. Яку роль виконує виклик super(...) у конструкторі підтипу?

`super(...)` викликає конструктор базового класу. Він дозволяє передати спільні значення до `Screening`, де вони перевіряються та зберігаються. Завдяки цьому підтипи не дублюють логіку ініціалізації спільних полів.

## 5. Що перевіряє анотація @Override?

`@Override` повідомляє компілятору, що метод повинен перевизначати метод базового класу або реалізовувати метод контракту. Якщо назву, параметри або типи випадково вказати неправильно, компілятор повідомить про помилку.

## 6. Що таке поліморфізм і як він усуває розгалуження за типом?

Поліморфізм дозволяє працювати з різними конкретними об'єктами через один спільний тип. У моєму проєкті код працює зі `Screening` та викликає `revenue()`. Java сама вибирає реалізацію `RegularScreening` або `PremiumScreening`, тому для формули виторгу не потрібна перевірка конкретного типу через `if`.

## 7. Коли краще використати інтерфейс, а коли абстрактний клас?

Інтерфейс доцільний, коли потрібно описати спільний контракт для типів, які не обов'язково мають спільний стан. Абстрактний клас зручніший, коли підтипи мають спільні поля, конструктор та частину реалізації. Для `Screening` обрано абстрактний клас через спільні поля та правила валідації.

## 8. Що означає відношення «є різновидом» і чим воно відрізняється від композиції?

«Є різновидом» означає, що підтип логічно є конкретнішою формою базового типу. `PremiumScreening` є різновидом `Screening`. Композиція означає відношення «має у складі». Наприклад, якби кіносеанс містив окремий об'єкт залу, це було б відношення композиції, а не спадкування.

## 9. Для чого використовують enum із полями та методами?

`enum` дозволяє визначити обмежений набір допустимих значень. Додавання полів і методів дозволяє зберігати разом із константою додаткову інформацію. У `ScreeningKind` для `REGULAR` і `PREMIUM` зберігаються текстові назви.

## 10. Чому значення enum можна порівнювати через ==?

Кожна enum-константа існує в єдиному екземплярі в межах JVM. Тому для двох значень одного enum оператор `==` коректно перевіряє, чи це та сама константа.

## 11. Які правила має виконувати пара equals/hashCode?

Якщо два об'єкти рівні за `equals()`, вони обов'язково повинні мати однаковий `hashCode()`. Рівність також повинна бути рефлексивною, симетричною, транзитивною та стабільною, поки значення, що беруть участь у порівнянні, не змінюються.

## 12. Чому змінне поле небезпечне для об'єкта, який є ключем HashMap?

Якщо після додавання ключа до `HashMap` змінити поле, яке використовується в `equals()` або `hashCode()`, hash-код може змінитися. Тоді об'єкт фактично опиниться не в тому hash-сегменті, в якому його шукатиме колекція, і ключ може стати неможливо нормально знайти.

## 13. Чому два об'єкти різних підтипів можуть бути нерівними за однакової назви?

Різні підтипи можуть мати різну семантику та додатковий стан. Наприклад, `RegularScreening` і `PremiumScreening` можуть мати однакову назву фільму, але один із них має `premiumFee` і використовує іншу формулу виторгу. Тому в моїй реалізації конкретний клас також враховується під час перевірки рівності.

## 14. Як поліморфна колекція обробляє об'єкти різних підтипів?

Колекція оголошується для базового типу, наприклад `List<Screening>`. До неї можна додати `RegularScreening` і `PremiumScreening`. Під час виклику перевизначеного методу Java виконає реалізацію фактичного підтипу кожного елемента.

## 15. Які тести доводять, що підтипи мають різну поведінку?

У `ScreeningHierarchyTest` окремо перевіряється `revenue()` звичайного сеансу та `revenue()` преміального сеансу з додатковою платою. Однаковий виклик методу через спільний контракт дає результат відповідно до конкретного підтипу.

## 16. Які тести доводять коректність рівності в HashSet?

Створюються два логічно рівні `RegularScreening` і додаються до `HashSet`. Після додавання розмір множини повинен дорівнювати одному. Також окремо перевіряється рівність об'єктів і однаковість їхніх hash-кодів.

## 17. Що контролює sealed і навіщо потрібен permits?

`sealed` обмежує набір класів, яким дозволено безпосередньо успадковувати базовий тип. `permits` явно перелічує дозволені підтипи. У моєму випадку `Screening` дозволяє тільки `RegularScreening` та `PremiumScreening`.

## 18. Чому switch за підтипами не повинен дублювати поліморфні методи?

Якщо формулу `revenue()` реалізувати в підтипах, а потім повторити ті самі формули в `switch`, одна логіка буде існувати у двох місцях. Це ускладнить підтримку та може спричинити розбіжності. Тому в моєму проєкті `switch` використовується лише для текстового опису, а виторг завжди обчислюється через `revenue()`.

## 19. Які попередні тести та результати потрібно зберегти після перебудови?

Потрібно зберегти перевірки зовнішньої поведінки, правила валідації, роботу `TicketSales`, обробку аргументів командного рядка та контрольні показники звіту. Для мого набору даних це 5 правильних і 5 неправильних записів, виторг 98700.00 грн, середня ціна 182.00 грн і максимум `sold` 150.

## 20. Яке рішення у Вашій ієрархії найкраще демонструє перевагу поліморфізму?

Найкращим прикладом є метод `revenue()`. Код статистики працює з `List<Screening>` і викликає один метод незалежно від конкретного підтипу. `RegularScreening` і `PremiumScreening` самостійно реалізують свої формули. Тому для додавання поведінки підтипу не потрібно переносити формулу до центрального коду звітності.
