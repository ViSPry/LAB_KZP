# 8. Клас Screening

Для представлення одного кіносеансу створено клас `Screening`.

Клас оголошено як `public final class Screening`.

Він містить п'ять полів:

- `private final String film`;
- `private final int hall`;
- `private final double ticketPrice`;
- `private final int sold`;
- `private final int durationMin`.

Використання `private` приховує поля від прямого доступу з інших класів.

Використання `final` означає, що після присвоєння значень у конструкторі ці поля не можуть бути переприсвоєні.

Сам клас також оголошено як `final`, тому створювати його підкласи неможливо.

---

# 9. Інкапсуляція

Інкапсуляція використовується для приховування внутрішнього стану об'єкта та контролю способу взаємодії з ним.

Поля `film`, `hall`, `ticketPrice`, `sold` та `durationMin` є приватними.

Для отримання їхніх значень використовуються getter-методи.

Публічні setter-методи в `Screening` відсутні.

Це не дозволяє спочатку створити правильний об'єкт, а потім перевести його в неправильний стан шляхом довільної зміни одного з полів.

# 10. Незмінність Screening

`Screening` реалізовано як незмінний клас.

Основні ознаки незмінності:

- клас оголошений як `final`;
- поля оголошені як `private final`;
- setter-методи відсутні;
- усі основні значення передаються під час створення;
- конструктор перевіряє коректність значень.

Після успішного створення `Screening` його стан не змінюється.

Це спрощує розуміння програми та зменшує кількість потенційних помилок, пов'язаних із неконтрольованою зміною стану.

# 11. Конструктор Screening

Конструктор `Screening` приймає назву фільму, номер залу, ціну квитка, кількість проданих квитків та тривалість.

Перед присвоєнням полів виконуються перевірки.

Якщо значення порушує інваріанти класу, генерується `IllegalArgumentException`.

Таким чином, неможливо успішно створити об'єкт `Screening` із некоректними значеннями.

# 13. Чому валідація виконується в конструкторі

Якби перевірка значень виконувалася лише в `Main`, інші частини програми могли б створити `Screening` без цієї перевірки.

Розміщення інваріантів у конструкторі робить їх обов'язковими для будь-якого способу створення об'єкта.

Перевірка спрацьовує при прямому виклику конструктора, використанні `Screening.fromCsv()` та використанні Builder.

Це дозволяє централізувати правила коректності предметної сутності.

# 14. Статичний фабричний метод fromCsv

Для перетворення одного CSV-рядка на предметний об'єкт реалізовано статичний метод `Screening.fromCsv(String line)`.

Метод виконує такі дії:

1. перевіряє, що рядок не є `null`;
2. розділяє його за символом `;`;
3. перевіряє кількість отриманих полів;
4. видаляє зайві пробіли;
5. перетворює числові значення;
6. передає результат конструктору `Screening`.

У результаті метод або повертає повністю коректний `Screening`, або повідомляє про помилку через виняток.

# 15. Обробка неправильного числового формату

Для перетворення числових значень використовуються стандартні методи `Integer.parseInt()` та `Double.parseDouble()`.

Якщо текст неможливо перетворити у відповідний числовий тип, Java генерує `NumberFormatException`.

У `fromCsv()` така ситуація перетворюється на `IllegalArgumentException` із повідомленням про неправильний числовий формат.

Це дозволяє зовнішньому коду однаково обробляти різні помилки одного CSV-запису.

Метод `toString()` використовується для текстового представлення об'єкта, але не є заміною формату CSV.

# 18. Record TicketSales

Для представлення результатів розрахунку створено `record TicketSales`.

Він містить такі компоненти:

- `validCount`;
- `invalidCount`;
- `totalRevenue`;
- `averageTicketPrice`;
- `maxSold`.

`record` добре підходить для цієї задачі, оскільки `TicketSales` є невеликим об'єктом-значенням, основним призначенням якого є зберігання готового набору результатів.

Java автоматично створює для компонентів `record` accessor-методи, а також стандартні реалізації `equals()`, `hashCode()` і `toString()`.

# 19. Валідація TicketSales

У компактному конструкторі `TicketSales` перевіряються основні інваріанти.

Використовуються такі правила:

- `validCount >= 0`;
- `invalidCount >= 0`;
- `totalRevenue` має бути скінченним та невід'ємним;
- `averageTicketPrice` має бути скінченним та невід'ємним;
- `maxSold >= 0`.

Отже, допоміжний об'єкт статистики також не може успішно створитися з явно неправильним станом.

# 20. Builder

У межах додаткового завдання із зірочкою для `Screening` реалізовано Builder.

При його використанні значення `film`, `hall`, `ticketPrice`, `sold` та `durationMin` можна встановлювати послідовно, а після цього викликати `build()`.

Builder робить створення об'єкта з декількома параметрами більш читабельним.

Особливо це корисно, коли під час читання коду потрібно одразу бачити, якому полю відповідає конкретне значення.

---

# 21. Builder не обходить валідацію

Важливою особливістю реалізації є те, що Builder не створює `Screening` в обхід основного конструктора.

Метод `build()` викликає конструктор `Screening`.

Тому при створенні через Builder застосовуються ті самі правила валідації, що й при прямому використанні конструктора або `fromCsv()`.

Наприклад, Builder не дозволить створити `Screening` із порожньою назвою фільму або від'ємною ціною.

# 22. Незмінність і безпечніша передача стану

Незмінний об'єкт після створення не змінює свій стан.

Якщо правильно створений `Screening` передається іншій частині програми, вона не може змінити його поля через setter-методи, оскільки таких методів немає.

Це зменшує ризик помилок, пов'язаних зі спільним змінним станом, і спрощує використання таких об'єктів у складніших програмах.

# 45. Контрольні питання

## 1. Яку проблему розв'язує клас-сутність порівняно з рядком і паралельними змінними?

Клас-сутність об'єднує пов'язані дані та правила роботи з ними в одному типі. Замість окремого зберігання назви фільму, залу, ціни, кількості проданих квитків і тривалості використовується один `Screening`. Це зменшує ризик переплутати значення та дозволяє розмістити правила валідації біля самих даних.

## 2. Що означають private і final у полях класу?

`private` означає, що поле не доступне напряму з інших класів. `final` означає, що після присвоєння значення полю його не можна переприсвоїти. У `Screening` поєднання `private final` допомагає реалізувати незмінний стан.

## 3. Що таке інкапсуляція і яку проблему вона запобігає?

Інкапсуляція — це приховування внутрішнього стану об'єкта та надання контрольованого способу взаємодії з ним. Вона запобігає довільній зміні внутрішніх даних з інших частин програми.

## 4. Чому перевірку інваріантів розміщують у конструкторі?

Конструктор є центральною точкою створення об'єкта. Якщо перевірка виконується в ньому, неможливо успішно створити `Screening` із неправильним станом незалежно від способу його створення.

## 5. Чим Objects.requireNonNull відрізняється від isBlank?

`Objects.requireNonNull()` перевіряє, що посилання не дорівнює `null`. Метод `isBlank()` перевіряє, чи рядок є порожнім або складається лише з пробільних символів. Для повної перевірки назви фільму необхідно враховувати обидві ситуації.

## 6. Чому відсутність setters допомагає зберегти коректний стан?

Без setters зовнішній код не може після створення об'єкта довільно змінити його поля. Якщо об'єкт пройшов перевірку конструктора, його стан надалі залишається коректним.

## 7. Які методи й властивості автоматично отримує record?

`record` автоматично отримує приватні фінальні поля для компонентів, accessor-методи, конструктор, а також реалізації `equals()`, `hashCode()` і `toString()`.

## 8. Чим record відрізняється від звичайного класу-сутності?

`record` призначений насамперед для компактного представлення об'єктів-значень. Він автоматично генерує значну частину стандартного коду. Звичайний клас надає більше свободи у визначенні структури, стану та поведінки.

## 9. Чому record не гарантує глибоку незмінність змінного списку?

Якщо компонент `record` посилається на змінний об'єкт, наприклад `ArrayList`, саме посилання не можна переприсвоїти, але вміст списку все одно може бути змінений. Тому `record` забезпечує незмінність компонентів як посилань, але не автоматично глибоку незмінність усіх вкладених об'єктів.

## 10. Для чого потрібен статичний фабричний метод fromCsv?

`fromCsv()` приховує деталі перетворення текстового CSV-рядка на предметний об'єкт. Зовнішньому коду достатньо передати рядок і отримати `Screening` або помилку валідації.

## 11. Де потрібно перехоплювати помилку розбору одного рядка?

Помилку окремого запису потрібно обробляти на рівні циклу читання файлу, щоб неправильний рядок не завершував роботу всієї програми. Після помилки програма повинна перейти до наступного запису.

## 12. Чому неправильний запис не можна додавати до списку до завершення перевірки?

Якщо додати об'єкт до списку до повної перевірки, у списку можуть з'явитися некоректні предметні дані. Спочатку потрібно успішно створити та перевірити об'єкт, і лише після цього додавати його до колекції.

## 13. Яке призначення toString і чому він не замінює формат CSV?

`toString()` використовується для зручного текстового представлення об'єкта, наприклад для налагодження. CSV є окремим форматом обміну даними з визначеними правилами та структурою, тому `toString()` не повинен автоматично вважатися CSV-представленням.

## 14. Для чого використовується Locale.ROOT?

`Locale.ROOT` використовується для нейтрального форматування, яке не залежить від мовних і регіональних налаштувань конкретної операційної системи.

## 15. Для чого потрібен Builder?

Builder дозволяє послідовно та зрозуміло задавати параметри складного об'єкта. Назви методів Builder показують, якому саме полю відповідає значення, тому код стає читабельнішим.

## 16. Чому Builder не повинен обходити конструктор?

Якщо Builder створюватиме об'єкт без перевірок конструктора, з'явиться альтернативний шлях створення неправильного стану. Тому `build()` повинен використовувати той самий конструктор з перевіркою інваріантів.

## 17. Для чого потрібні позитивні, граничні та негативні тести?

Позитивні тести перевіряють звичайні правильні дані. Граничні тести перевіряють значення біля меж дозволеного діапазону. Негативні тести перевіряють, що неправильні значення дійсно відхиляються.

## 18. Що виконує Maven verify?

Фаза `verify` запускає попередні фази життєвого циклу Maven, включаючи компіляцію, тести та пакування, а також підключені до `verify` додаткові перевірки. У цьому проєкті до неї також прив'язано SpotBugs.

## 19. Навіщо запускати CI на декількох операційних системах?

Код може поводитися по-різному через особливості файлових шляхів, кодування, shell-команд або середовища. Перевірка на Ubuntu, Windows і macOS допомагає підтвердити кросплатформність проєкту.

## 20. Чому після рефакторингу важливо зберегти старі тести?

Рефакторинг повинен покращувати внутрішню структуру коду без небажаної зміни його зовнішньої поведінки. Старі тести працюють як перевірка того, що функціональність попередньої версії не була випадково зламана.

GitHub Actions перевіряє проєкт на Ubuntu, Windows та macOS і формує JAR artifact. Поточна версія проєкту — **2.0.0**, а виконуваний файл має назву `lab01-2.0.0.jar`.

Таким чином, у лабораторній роботі №2 вдалося покращити внутрішню архітектуру програми, додати чітку предметну модель, централізувати валідацію, підвищити тестованість коду та при цьому повністю зберегти функціональну поведінку, реалізовану в лабораторній роботі №1.

Після створення фінального Pull Request у звіт залишиться додати посилання на PR, фінальний запуск GitHub Actions та workflow artifact, а після merge — зафіксувати фінальний Git-тег `v2.0.0`.
