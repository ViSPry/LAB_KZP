## 3. Постановка задачі

Для варіанта 19 предметною областю є кінотеатр.

Формат CSV залишається таким самим, як у лабораторній роботі №1:

```text
film;hall;ticketPrice;sold;durationMin
```

Поля:
- `film` — назва фільму;
- `hall` — номер кінозалу;
- `ticketPrice` — ціна одного квитка;
- `sold` — кількість проданих квитків;
- `durationMin` — тривалість фільму у хвилинах.

Після рефакторингу один правильний CSV-запис повинен представлятися об'єктом `Screening`, а результати статистичних розрахунків — об'єктом `TicketSales`.

Головною умовою є збереження зовнішньої поведінки програми.

## 8. Предметний клас Screening

Для представлення одного кіносеансу створено:
```java
public final class Screening
```

Основні поля:
```java
private final String film;
private final int hall;
private final double ticketPrice;
private final int sold;
private final int durationMin;
```

`film` зберігає назву фільму, `hall` — номер залу, `ticketPrice` — ціну квитка, `sold` — кількість проданих квитків, `durationMin` — тривалість.

## 9. Інкапсуляція

Усі поля `Screening` оголошені `private`, тому зовнішній код не має прямого доступу до стану.

Поля також оголошені `final`, а setter-методи відсутні.

Для читання використовуються:
```text
getFilm()
getHall()
getTicketPrice()
getSold()
getDurationMin()
```

Отже, `Screening` контролює власний стан і не дозволяє довільно змінювати його після створення.

## 10. Незмінність Screening

`Screening` реалізовано як immutable-об'єкт:
- клас є `final`;
- поля є `private final`;
- setter-методів немає;
- значення встановлюються під час створення;
- конструктор перевіряє їх правильність.

Після успішного створення стан `Screening` не змінюється.

## 11. Конструктор і валідація

Конструктор:
```java
public Screening(
        String film,
        int hall,
        double ticketPrice,
        int sold,
        int durationMin)
```

У ньому перевіряються предметні інваріанти.

Правила:
```text
film != null і !film.isBlank()
hall > 0
ticketPrice >= 0
ticketPrice є скінченним числом
sold >= 0
durationMin > 0
```

При порушенні правила генерується `IllegalArgumentException`.

Наприклад, для порожньої назви:
```text
назва фільму порожня
```

Для неправильного номера залу:
```text
номер залу має бути додатним
```

Для від'ємної ціни:
```text
ціна квитка має бути невід'ємною
```

## 12. Чому валідація знаходиться в конструкторі

Конструктор є єдиною точкою перевірки предметного стану.

Це означає, що:
```text
new Screening(...)
Screening.fromCsv(...)
Screening.builder().build()
```

у кінцевому результаті використовують однакові правила.

Таким чином у програмі не дублюється предметна валідація.

## 13. Метод fromCsv()

Для створення об'єкта з CSV реалізовано:
```java
public static Screening fromCsv(String line)
```

Метод:
1. перевіряє вхідний рядок;
2. розділяє його на поля;
3. перевіряє кількість полів;
4. перетворює числові значення;
5. викликає конструктор `Screening`.

Для розділення використано:
```java
line.split(";", -1)
```

`-1` дозволяє не втрачати порожні поля наприкінці рядка.

Правильний запис повинен містити рівно 5 полів.

## 14. Числовий формат

Для чисел використовуються:
```java
Integer.parseInt()
Double.parseDouble()
```

Якщо рядок містить, наприклад:
```text
Титанік;abc;170.00;100;195
```

виникає `NumberFormatException`.

`fromCsv()` перетворює таку ситуацію на `IllegalArgumentException` з повідомленням:
```text
неправильний числовий формат
```

## 15. Розподіл відповідальності

`fromCsv()` відповідає за формат CSV:
- кількість полів;
- розділення;
- перетворення рядків на числа.

Конструктор відповідає за предметні правила:
- правильну назву;
- номер залу;
- ціну;
- кількість продажів;
- тривалість.

Такий розподіл робить код простішим і не прив'язує сам `Screening` лише до CSV.

## 16. Метод toString()

У `Screening` перевизначено `toString()`.

Для форматування використовується:
```java
Locale.ROOT
```

Це забезпечує передбачуване представлення числових значень незалежно від системної локалі.

## 17. Record TicketSales

Для результатів статистики створено:
```java
public record TicketSales(
        int validCount,
        int invalidCount,
        double totalRevenue,
        double averageTicketPrice,
        int maxSold)
```

Компоненти означають:
- `validCount` — правильні записи;
- `invalidCount` — неправильні;
- `totalRevenue` — загальний виторг;
- `averageTicketPrice` — середня ціна;
- `maxSold` — максимальна кількість проданих квитків.

## 18. Переваги record

`TicketSales` є об'єктом-значенням, тому `record` добре відповідає його призначенню.

Java автоматично створює:
```text
validCount()
invalidCount()
totalRevenue()
averageTicketPrice()
maxSold()
equals()
hashCode()
toString()
```

Не потрібно вручну створювати звичайний клас із великою кількістю шаблонного коду.

## 19. Compact constructor

У `TicketSales` використано compact constructor.

Перевіряється:
```text
validCount >= 0
invalidCount >= 0
totalRevenue >= 0
averageTicketPrice >= 0
maxSold >= 0
```

Для `double` також перевіряється скінченність.

Тому `TicketSales` також не може містити некоректний стан.

## 20. Immutable Builder

У межах додаткового завдання реалізовано `Screening.Builder`.

Приклад:
```java
Screening screening = Screening.builder()
        .film("Інтерстеллар")
        .hall(3)
        .ticketPrice(160.0)
        .sold(150)
        .durationMin(169)
        .build();
```

Builder робить створення об'єкта читабельнішим.

Особливо це корисно для конструктора з декількома параметрами однакових або подібних типів.

## 21. Builder не обходить перевірки

`build()` створює об'єкт через основний конструктор:
```java
return new Screening(
        film,
        hall,
        ticketPrice,
        sold,
        durationMin);
```

Тому неправильне значення, наприклад:
```text
hall = -1
```

буде відхилено конструктором.

Це окремо перевіряється JUnit-тестом `builderCannotBypassValidation`.

## 22. Незмінність і багатопотоковість

Незмінний об'єкт не може несподівано змінити свій стан після передачі іншій частині програми.

Це зменшує кількість помилок, пов'язаних зі спільним змінюваним станом.

У поточній програмі власна багатопотокова обробка не реалізована, але immutable-підхід робить такі об'єкти простішими для безпечного спільного читання.

## 24. Обчислення статистики

Для правильних записів розраховується загальний виторг:
```text
totalRevenue = Σ(ticketPrice × sold)
```

Середня ціна:
```text
averageTicketPrice = Σ(ticketPrice) / validCount
```

Також визначається максимальне значення `sold`.

Результат повертається як `TicketSales`.

# 40. Контрольні питання

### 1. Що таке інкапсуляція?
Інкапсуляція — приховування внутрішнього стану об'єкта та надання контрольованого публічного інтерфейсу для роботи з ним.

### 2. Чому поля Screening private?
Щоб зовнішній код не міг безпосередньо змінити стан об'єкта.

### 3. Навіщо final?
`final` не дозволяє перепризначити поле після його ініціалізації. `final class` також забороняє успадкування.

### 4. Чому немає setter-методів?
Тому що `Screening` реалізований як незмінний об'єкт.

### 5. Що таке інваріант?
Це умова, яка повинна виконуватися для будь-якого правильного стану об'єкта, наприклад `hall > 0`.

### 6. Чому валідація знаходиться в конструкторі?
Щоб усі способи створення `Screening` використовували однакові правила.

### 7. Що таке статичний фабричний метод?
Це статичний метод, який створює і повертає об'єкт. У проєкті це `Screening.fromCsv()`.

### 8. Для чого потрібен fromCsv()?
Для перетворення одного CSV-рядка на предметний об'єкт `Screening`.

### 9. Для чого використано split(";", -1)?
Щоб зберігати порожні поля наприкінці рядка і правильно перевіряти структуру CSV.

### 10. Що таке record?
`record` — спеціальна форма Java-класу для компактного представлення об'єктів-значень.

### 11. Чому TicketSales є record?
Він лише зберігає пов'язані результати статистичних розрахунків і не потребує змінюваного стану.

### 12. Що таке compact constructor?
Це форма конструктора `record`, у якій можна перевірити його компоненти.

### 13. Що таке Builder?
Builder — шаблон проєктування для покрокового та читабельного створення об'єктів.

### 14. Чому Builder не обходить валідацію?
Тому що `build()` викликає основний конструктор `Screening`.

### 15. Що означає immutable?
Це означає, що стан об'єкта не змінюється після його створення.

### 16. Чому immutable-об'єкти корисні для потоків?
Відсутність зміни стану зменшує проблеми, пов'язані з одночасним доступом декількох потоків.

### 17. Навіщо Locale.ROOT?
Щоб форматування не залежало від локальних налаштувань операційної системи.

### 18. Як перевірено збереження поведінки?
Порівняно однаковий CSV до та після рефакторингу. Усі п'ять статистичних показників збіглися.

### 19. Навіщо залишено старі тести?
Вони працюють як regression tests та підтверджують, що новий код не зламав стару функціональність.

### 20. Що виконує clean verify?
`clean` видаляє попередні результати збирання, після чого Maven компілює код, запускає тести, створює JAR і виконує перевірки фази `verify`, включно зі SpotBugs.

У лабораторній роботі №2 виконано рефакторинг Java-застосунку предметної області «Кінотеатр».
