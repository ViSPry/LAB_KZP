# Кінотеатр — лабораторні роботи №1–2

Навчальний Java-проєкт з дисципліни «Кросплатформні засоби програмування».

Проєкт реалізує консольну програму для обробки даних кінотеатру. Лабораторна робота №2 продовжує ЛР №1: рядкове представлення предметних даних замінено власними класами та `record` без зміни зовнішньої поведінки програми.

## Лабораторна робота №2

**Тема:** Класи, `record` і інкапсуляція в Java-проєкті.

**Варіант:** 19 — «Кінотеатр».

Основна мета ЛР №2 — рефакторинг предметної логіки ЛР №1 із використанням власних типів даних, інкапсуляції, незмінних об'єктів та автоматизованого тестування.

## Структура предметної моделі

У ЛР №2 додано клас-сутність:

`Screening`

Він представляє один запис про кіносеанс і містить:

- `film` — назва фільму;
- `hall` — номер залу;
- `ticketPrice` — ціна квитка;
- `sold` — кількість проданих квитків;
- `durationMin` — тривалість фільму у хвилинах.

Поля класу оголошені як `private final`. Публічні сеттери відсутні, тому після створення стан об'єкта не можна змінити.

Перевірка коректності значень виконується в конструкторі.

Для створення об'єкта з CSV-рядка використовується статичний фабричний метод:

`Screening.fromCsv(String line)`

Також реалізовано `Builder`, який спрощує створення об'єктів `Screening`. Метод `build()` викликає основний конструктор, тому Builder не може обійти перевірку інваріантів.

## Record

Для зберігання підсумкової статистики використовується:

`TicketSales`

Це Java `record`, який містить:

- кількість правильних записів;
- кількість неправильних записів;
- загальний виторг;
- середню ціну квитка;
- максимальну кількість проданих квитків.

Для компонентів `TicketSales` також перевіряються основні інваріанти.

## Формат вхідного CSV

Файл містить записи у форматі:


film;hall;ticketPrice;sold;durationMin


Приклад:


Дюна 2;1;180.00;120;166
Оппенгеймер;2;200.00;150;180


Кожний рядок повинен містити рівно 5 полів.

## Валідація

Запис вважається правильним, якщо:

- назва фільму не порожня;
- номер залу більший за `0`;
- ціна квитка є скінченним невід'ємним числом;
- кількість проданих квитків не є від'ємною;
- тривалість фільму більша за `0`;
- числові поля мають правильний формат;
- CSV-рядок містить рівно 5 полів.

Некоректний запис не додається до списку правильних записів, а програма продовжує обробку наступних рядків.

## Показники звіту

Програма обчислює:

1. кількість правильних записів;
2. кількість неправильних записів;
3. загальний виторг;
4. середню ціну квитка;
5. максимальну кількість проданих квитків.

Після рефакторингу результати для контрольного набору даних залишилися такими самими, як у ЛР №1:


Правильних записів: 5
Неправильних записів: 5
Загальний виторг: 98700.00 грн
Середня ціна квитка: 182.00 грн
Максимальна кількість проданих квитків: 150


## Збірка

У Windows:


.\mvnw.cmd clean verify

У Linux/macOS:


./mvnw clean verify


Команда виконує компіляцію, автоматичні тести, перевірку SpotBugs та створення JAR.

Після успішної збірки створюється:


target/lab01-2.0.0.jar


## Запуск програми

Стандартний запуск:


java -jar target\lab01-2.0.0.jar


За замовчуванням використовуються:


data/input.csv
out/report.txt


Власні шляхи:


java -jar target\lab01-2.0.0.jar --input data/input.csv --output out/report.txt
`

Перегляд довідки:

`lab01` залишається Maven `artifactId` проєкту, успадкованого з першої лабораторної роботи. Версія реалізації ЛР №2 — `2.0.0`.

## Тестування

У проєкті використовуються JUnit 5 тести.

Загальна кількість тестів:

28


Тести розподілені між:

- `MainTest` — перевірка поведінки консольної програми та збереження функціональності ЛР №1;
- `ScreeningTest` — перевірка конструктора, валідації, `fromCsv()` і Builder;
- `TicketSalesTest` — перевірка `record` та його інваріантів.

Перевіряються позитивні, граничні та негативні сценарії.

## SpotBugs

SpotBugs підключений до Maven і запускається під час фази:


verify

Тому команда:


.\mvnw.cmd clean verify


виконує не лише тести, а й статичний аналіз коду.

## GitHub Actions

CI запускається на трьох операційних системах:

- Ubuntu;
- Windows;
- macOS.

На кожній ОС виконується Maven `verify`.

Workflow також публікує створений JAR як GitHub Actions artifact.
