### Взаємодія компонентів

Програма запускається через `Main`, який передає аргументи класу `CinemaController`. Контролер використовує `CommandLineParser` для визначення режиму роботи.

Для формування звіту викликається `CinemaReportService`, який використовує `CinemaCsvParser` і `TicketSalesService`.

Режим `--streams` обслуговує `StreamDemoService`, що використовує `ScreeningQueries`. Режим `--storage` запускає `StorageController`, який взаємодіє зі `StorageService`.

Рефакторинг зберіг усі режими запуску: `--help`, `--version`, `--streams`, `--storage`, `--input` та `--output`.

## Предметна модель

`Screening` — абстрактний `sealed`-клас, який дозволяє лише два `final`-підтипи:

- `RegularScreening` — звичайний сеанс; виторг: `ticketPrice * sold`.
- `PremiumScreening` — преміальний сеанс; виторг: `(ticketPrice + premiumFee) * sold`.

`ScreeningKind` містить значення `REGULAR` і `PREMIUM`. `TicketSales` — `record` для підсумків обробки CSV. Усі види сеансів обробляються через `List<Screening>`, а виторг розраховується поліморфним викликом `screening.revenue()`.

У ЛР №4 до `Screening` додано незмінне поле `startTime` типу `LocalTime`. Воно використовується для сортування та пошуку. Нові конструктори приймають час початку; старі конструктори збережені для сумісності й задають технічне значення `00:00`, коли час не передано. Значення `00:00` у такому разі **не означає підтверджений фактичний час показу**.

Основні інваріанти: непорожня назва фільму; додатний номер залу та тривалість; скінченна невід'ємна ціна; невід'ємна кількість продажів; ненульовий `startTime`. Для преміального сеансу доплата також має бути скінченною й невід'ємною.

Методи `equals()` і `hashCode()` враховують клас, спільні поля, час початку та специфічний стан підтипу (зокрема `premiumFee`).

## ЛР №4: Stream API (варіант 19)

Запити зосереджено в класі `ScreeningQueries`. Вони не змінюють вхідний список.

| Метод | Призначення | Stream API |
|---|---|---|
| `filterBySold(screenings, threshold)` | Сеанси, де продано **понад** поріг | `filter`, `toList` |
| `filmNames(screenings)` | Назви фільмів у початковому порядку, включно з повтореннями | `map`, `toList` |
| `revenueByHall(screenings)` | Сума поліморфного виторгу за залом | `groupingBy`, `summingDouble` |
| `ticketPriceStatistics(screenings)` | Кількість, сума, мінімум, максимум, середнє значення ціни | `summarizingDouble` |
| `topBySoldAndTime(screenings, n)` | Top-N: спочатку продажі за спаданням, при рівності — час за зростанням | `sorted`, `limit`, `toList` |
| `findByFilmAndTime(screenings, film, startTime)` | Перший збіг назви фільму та часу | `filter`, `findFirst`, `Optional` |
| `countByHallAndKind(screenings)` | **Додаткове завдання:** кількість сеансів за залом і типом | вкладений `groupingBy`, `counting` |

Для `topBySoldAndTime` значення `n < 0` спричиняє `IllegalArgumentException`, `n = 0` повертає порожній список, а `n` більше розміру колекції повертає всі наявні елементи. `findByFilmAndTime` повертає `Optional.empty()`, якщо збігу немає.

## CSV і сумісність

Формат CSV **не змінювався** з попередніх лабораторних робіт:

`film;hall;ticketPrice;sold;durationMin`

Приклад:

`Дюна 2;1;180.00;120;166`

Кожний рядок має містити рівно п'ять полів. `Screening.fromCsv()` створює `PremiumScreening` для залу 1 (з доплатою `0.0`) та `RegularScreening` для інших залів. У старому CSV **немає поля часу**; час у демонстрації Stream API задається під час створення тестових об'єктів.

Контрольні результати старого CSV збережено:

| Показник | Значення |
|---|---:|
| Правильних записів | 5 |
| Неправильних записів | 5 |
| Загальний виторг | 98700.00 грн |
| Середня ціна квитка | 182.00 грн |
| Максимальна кількість продажів | 150 |

## Збірка та запуск

Потрібен **JDK 21**. У Windows, у корені репозиторію:

```powershell
.\mvnw.cmd clean verify
```

У Linux/macOS:

```bash
./mvnw clean verify
```

Виконуваний JAR після збірки: `target/lab01-5.0.0.jar`. Назва `lab01` — незмінний Maven `artifactId` проєкту.

```powershell
# Стандартний запуск: data/input.csv -> out/report.txt
java -jar .\target\lab01-5.0.0.jar

# Власні шляхи
java -jar .\target\lab01-5.0.0.jar --input data/input.csv --output out/report.txt

# Демонстрація Stream API
java -jar .\target\lab01-5.0.0.jar --streams

# Довідка і версія
java -jar .\target\lab01-5.0.0.jar --help
java -jar .\target\lab01-5.0.0.jar --version
```

Очікувана відповідь на `--version`: `lab01 version 5.0.0`.
**Версіонування:** єдиним джерелом версії застосунку є `pom.xml`.
Під час Maven-збірки версія автоматично записується до JAR-маніфесту
як `Implementation-Version`. Параметри `--version` і `--help`
отримують її програмно, без жорстко заданих номерів версій у Java-коді.

## ЛР №5: Generic Repository, CSV та JSON

У лабораторній роботі №5 (варіант 19 «Кінотеатр») реалізовано параметризоване сховище записів і механізми імпорту та експорту даних.

### Основні компоненти

| Компонент | Призначення |
|---|---|
| `Repository<T>` | Універсальне сховище з методами `add`, `all`, `find` |
| `ScreeningRecord` | Модель сеансу: фільм, зал, час, ціна, продані квитки |
| `CsvColumn` | Анотація для позначення полів експорту |
| `CsvExporter` | Універсальний CSV-експортер на основі Reflection |
| `CsvParser` | Розбір CSV, включно з лапками та багаторядковими значеннями |
| `ScreeningCsvImporter` | Імпорт CSV у список `ScreeningRecord` |
| `DataStorageException` | Виняток для помилок зберігання й обробки даних |
| `Exporter<T>` | Спільний інтерфейс експортерів |
| `JsonExporter<T>` | Додатковий JSON-експортер |
| `ReflectionFieldCache` | Потокобезпечний кеш метаданих полів |

### CSV-формат лабораторної №5

Новий формат експорту використовує роздільник `,` і заголовки, задані анотацією `@CsvColumn`.

Порядок полів визначається алфавітним сортуванням назв Java-полів:

`фільм,зал,продано,час,ціна`

CSV-експортер підтримує екранування ком, подвійних лапок і переносів рядків. Імпортер забезпечує перевірку структури CSV та перетворення значень у відповідні типи Java.

Цей формат відрізняється від початкового CSV лабораторних №1–4. Попередня логіка обробки CSV збережена для сумісності.

### Додаткові завдання

1. **JSON-експорт:** реалізовано `JsonExporter<T>` через спільний інтерфейс `Exporter<T>`.
2. **Кешування Reflection:** метадані полів зберігаються в `ConcurrentHashMap`.
3. **Успадковані поля:** експортери підтримують анотовані поля батьківських класів без дублювання однойменних полів.
