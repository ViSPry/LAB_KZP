# Кінотеатр — лабораторні роботи №1–3

Навчальний Java-проєкт з дисципліни «Кросплатформні засоби програмування».

Проєкт реалізує консольну програму для обробки даних кінотеатру та послідовно розвивається в межах лабораторних робіт.

У ЛР №1 реалізовано базову обробку CSV-файлу, формування статистики, Maven-збірку, тестування та CI.

У ЛР №2 рядкове представлення предметних даних замінено власними типами `Screening` і `TicketSales`, реалізовано інкапсуляцію та перевірку інваріантів.

У ЛР №3 предметну модель розширено за допомогою спадкування, інтерфейсу поліморфної поведінки через базовий тип, `enum`, перевизначення методів, `equals()` / `hashCode()`, гетерогенної колекції та sealed-ієрархії.

## Лабораторна робота №3

**Тема:** Спадкування, інтерфейси й поліморфізм у Java-проєкті.

**Варіант:** 19 — «Кінотеатр».

**Версія проєкту:** `3.0.0`.

Основна мета ЛР №3 — розширити модель ЛР №2 так, щоб різні типи кіносеансів мали спільний базовий тип, але могли реалізовувати власну поведінку. При цьому зовнішня поведінка програми та результати обробки контрольного CSV-файлу збережені.

## Структура предметної моделі

Основою моделі є абстрактний клас:

`Screening`

У ЛР №3 він утворює sealed-ієрархію:

`Screening`
- `RegularScreening`
- `PremiumScreening`

Оголошення базового класу обмежує допустимі підтипи за допомогою `sealed` і `permits`.

Конкретні класи `RegularScreening` і `PremiumScreening` оголошені як `final`.

Це робить ієрархію закритою та дозволяє компілятору знати всі допустимі реалізації `Screening`.

## Базовий клас Screening

`Screening` містить спільний стан кіносеансу:

- `film` — назва фільму;
- `hall` — номер залу;
- `ticketPrice` — базова ціна квитка;
- `sold` — кількість проданих квитків;
- `durationMin` — тривалість фільму у хвилинах.

Поля є `private final`.

Базовий клас відповідає за спільні інваріанти, доступ до даних, перетворення CSV-рядка та спільну частину логіки рівності об'єктів.

Для створення об'єкта з CSV використовується:

`Screening.fromCsv(String line)`

Фабричний метод створює конкретний підтип `Screening`, не змінюючи початковий п'ятипольний формат CSV.

У поточній реалізації сеанс у залі №1 створюється як `PremiumScreening`, а сеанси в інших залах — як `RegularScreening`.

Це дозволяє використовувати різні підтипи без додавання нового поля до CSV та без зміни формату даних попередніх лабораторних робіт.

## Валідація

Спільні інваріанти перевіряються перед збереженням стану базового об'єкта.

Запис вважається правильним, якщо:

- назва фільму не порожня;
- номер залу більший за `0`;
- ціна квитка є скінченним невід'ємним числом;
- кількість проданих квитків не є від'ємною;
- тривалість фільму більша за `0`;
- числові поля мають правильний формат;
- CSV-рядок містить рівно 5 полів.

Для внутрішнього передавання вже перевірених даних використовується приватний `ValidatedData record`.

Такий підхід також дозволив усунути попередження SpotBugs `CT_CONSTRUCTOR_THROW` без вимкнення або придушення перевірки.

## RegularScreening

`RegularScreening` представляє звичайний кіносеанс.

Клас успадковує спільні дані та інваріанти від `Screening`.

Поліморфна операція:

`revenue()`

для звичайного сеансу обчислюється як:

`ticketPrice * sold`

Метод `getKind()` повертає:

`ScreeningKind.REGULAR`

## PremiumScreening

`PremiumScreening` представляє преміальний кіносеанс.

Крім спільних полів `Screening`, він містить:

`premiumFee`

Це додаткова плата до базової ціни квитка.

Значення `premiumFee` повинно бути скінченним та невід'ємним.

Поліморфний метод `revenue()` для преміального сеансу використовує формулу:

`(ticketPrice + premiumFee) * sold`

Метод `getKind()` повертає:

`ScreeningKind.PREMIUM`

Для об'єктів, створених зі старого CSV-формату, додаткова плата дорівнює `0.0`. Завдяки цьому результати контрольного набору даних залишаються сумісними з ЛР №1 та ЛР №2.

## ScreeningKind

Для представлення виду кіносеансу використовується:

`ScreeningKind`

Enum містить значення:

- `REGULAR` — звичайний сеанс;
- `PREMIUM` — преміальний сеанс.

Кожне значення має текстову назву, яка може використовуватися під час виведення інформації про об'єкт.

## Поліморфізм

Обробка предметних об'єктів виконується через спільний тип:

`List<Screening>`

Один список може одночасно містити `RegularScreening` і `PremiumScreening`.

Для обчислення виторгу програма викликає:

`screening.revenue()`

Конкретна реалізація вибирається динамічно залежно від фактичного типу об'єкта.

Центральний `if` або `switch` для визначення формули виторгу не використовується.

Таким чином, логіка обчислення виторгу знаходиться безпосередньо у відповідному підтипі.

## Sealed-ієрархія та pattern matching

Як додаткове розширення реалізовано sealed-ієрархію:

`Screening permits RegularScreening, PremiumScreening`

У `Main` також використовується pattern matching `switch` для формування текстового опису конкретного виду сеансу.

Оскільки `Screening` є `sealed`, компілятор знає всі дозволені підтипи та може перевіряти повноту такого `switch`.

Pattern matching не використовується для обчислення виторгу. Виторг залишається поліморфною операцією `revenue()`.

Таким чином, `switch` не дублює основну поліморфну бізнес-логіку.

## equals() і hashCode()

Для ієрархії `Screening` реалізовано узгоджені `equals()` і `hashCode()`.

Під час порівняння враховуються:

- конкретний клас об'єкта;
- назва фільму;
- номер залу;
- ціна квитка;
- кількість проданих квитків;
- тривалість;
- додатковий стан конкретного підтипу.

Для `PremiumScreening` додатково враховується `premiumFee`.

Тому два преміальні сеанси з однаковими базовими даними, але різною додатковою платою, не вважаються однаковими.

Коректність контракту `equals()` / `hashCode()` додатково перевіряється за допомогою `HashSet`.

## Record

Для зберігання підсумкової статистики з ЛР №2 продовжує використовуватися:

`TicketSales`

Це Java `record`, який містить:

- кількість правильних записів;
- кількість неправильних записів;
- загальний виторг;
- середню ціну квитка;
- максимальну кількість проданих квитків.

Для компонентів `TicketSales` перевіряються основні інваріанти.

## Формат вхідного CSV

Формат вхідних даних не змінено:

`film;hall;ticketPrice;sold;durationMin`

Приклад:

`Дюна 2;1;180.00;120;166`

`Оппенгеймер;2;200.00;95;180`

Кожний рядок повинен містити рівно 5 полів.

## Показники звіту

Програма обчислює:

1. кількість правильних записів;
2. кількість неправильних записів;
3. загальний виторг;
4. середню ціну квитка;
5. максимальну кількість проданих квитків.

Після переходу до поліморфної моделі результати контрольного набору даних залишилися такими самими:

Правильних записів: 5

Неправильних записів: 5

Загальний виторг: 98700.00 грн

Середня ціна квитка: 182.00 грн

Максимальна кількість проданих квитків: 150

Таким чином, внутрішня архітектура програми змінилася, але її основна зовнішня поведінка збережена.

## Тестування

Для автоматизованого тестування використовується JUnit 5.

Тести розподілені між:

- `MainTest` — поведінка консольної програми та сумісність із попередніми лабораторними роботами;
- `ScreeningTest` — спільні інваріанти та `fromCsv()`;
- `ScreeningHierarchyTest` — підтипи, `ScreeningKind`, поліморфізм, `equals()` / `hashCode()` та використання `HashSet`;
- `TicketSalesTest` — перевірка `TicketSales record` та його інваріантів.

Перевіряються позитивні, граничні та негативні сценарії.

Повна перевірка виконується командою:

`.\mvnw.cmd clean verify`

## SpotBugs

SpotBugs підключений до Maven та запускається у фазі `verify`.

Під час реалізації ЛР №3 SpotBugs виявив проблему `CT_CONSTRUCTOR_THROW` для конструктора абстрактного `Screening`.

Проблему усунуто структурною зміною реалізації: перевірка значень виконується до присвоєння стану через окремий механізм валідації та приватний `ValidatedData record`.

Попередження не придушувалося через `@SuppressFBWarnings`.
