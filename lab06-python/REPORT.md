## 2. Стан проєкту до і після ЛР №7

### 2.1. Стан до рефакторингу

Попередній Python-етап реалізовував читання CSV, перевірку полів, аналіз продажів, текстовий звіт і консольний інтерфейс.
Його основою був модульний пакет `kzp_lab06`, що мав тести, конфігурацію `pyproject.toml`, пакетування wheel і CI на трьох операційних системах.

У методичних вказівках початкова модель подана як `dict[str, object]`, для якого перевірки й обчислення розміщені у зовнішніх функціях.
У фактичній реалізації ЛР №6 цього репозиторію `Screening` уже був незмінною `@dataclass(frozen=True)` із властивістю `revenue`.
Тому практичний перехід у цьому проєкті — **від простої dataclass-сутності до звичайного класу з контрольованими setter, підтипами й поліморфним методом**, а не буквальне перетворення словника на об'єкт уперше.
Це уточнення важливе для достовірного порівняння коду до і після роботи.

### 2.2. Стан після рефакторингу

У ЛР №7 клас `Screening` став звичайним класом із приватизованими за домовленістю внутрішніми полями та публічними властивостями.
Підтипи `RegularScreening` і `PremiumScreening` реалізують власні формули доходу.
`analysis.py` звертається до методу `revenue()` і не визначає формулу за назвою класу.
`loader.py` створює об'єкти `RegularScreening` з CSV-рядків.
`protocols.py` задає структурний контракт `ScreeningLike`.
`report_context.py` містить власний контекстний менеджер `SafeReportFile`.

### 2.4. Наслідки переходу

Перевага об'єктної моделі полягає в тому, що правила коректності стану знаходяться поруч із самими полями.
Новий підтип може змінити спосіб розрахунку доходу без переписування кожної функції аналізу.
Протокол зменшує зв'язність модулів, а поведінкові тести перевіряють контракт, а не тільки конкретну реалізацію.

Водночас об'єкти потребують додаткової пам'яті й більшого обсягу коду порівняно з простими словниками.
Для такого компромісу важливо не вигадувати числових переваг: окремий вимір пам'яті `dict` проти об'єктів ще не проводився.

## 3. Модель кіносеансу: клас, поля та інваріанти

### 3.1. Базовий клас `Screening`

Базовий клас оголошено у `src/kzp_lab06/models.py`.
Його конструктор приймає п'ять параметрів:

| Поле | Тип | Значення |
|---|---|---|
| `film` | `str` | Назва фільму |
| `hall` | `str` | Ідентифікатор залу |
| `start` | `datetime` | Локальні дата і час сеансу |
| `price` | `Decimal` | Ціна квитка |
| `sold` | `int` | Кількість проданих квитків |

`__init__` встановлює значення через властивості, тому їх перевірка виконується вже під час створення об'єкта.
Той самий setter повторно перевіряє дані під час подальшого присвоєння.

### 3.2. Властивості `film` та `hall`

Назва фільму й ідентифікатор залу повинні бути непорожніми рядками.
Відхиляються значення неправильного типу та рядки, що складаються тільки з пробілів.
Використання `strip()` дозволяє перевірити, чи містить текст змістовні символи.

### 3.3. Властивість `start`

Час початку повинен мати тип `datetime`.
У цій реалізації очікується локальний час без `tzinfo`.
Значення іншого типу або час із часовою зоною відхиляються.
Це узгоджується з контрольним CSV, у якому час записано у форматі `2026-11-02T18:00`.

### 3.4. Властивість `price`

Ціна повинна бути об'єктом `Decimal`, бути скінченною та невід'ємною.
Нульова ціна допускається; від'ємна ціна, `NaN` та нескінченність — ні.
Використання `Decimal` дає десяткову арифметику, придатну для грошових сум.

### 3.5. Властивість `sold`

Кількість продажів повинна бути саме цілим числом `int` і бути не меншою за нуль.
Перевірка `type(value) is int` навмисно відхиляє `bool`, оскільки в Python `bool` є підкласом `int`, але не є коректним значенням кількості квитків.
Нульові продажі допустимі.

### 3.6. Як працює setter

Спрощена ілюстрація контракту властивості `sold`:

```python
@property
def sold(self) -> int:
    return self._sold

@sold.setter
def sold(self, value: int) -> None:
    if type(value) is not int or value < 0:
        raise ValueError("Кількість продажів має бути невід'ємним цілим числом")
    self._sold = value
```

Цей приклад пояснює механізм, а не претендує на дослівне відтворення всіх повідомлень фактичного модуля.
Усередині setter запис здійснюється у `_sold`, а не в `self.sold`, щоб не створювати нескінченну рекурсію.
Префікс `_` означає домовленість про внутрішнє поле, а не абсолютну заборону доступу ззовні.

### 3.7. Граничні та помилкові значення

Для `sold` перевірено значення `0`, позитивне число, `-1` і `True`.
Для `price` — `0`, від'ємне значення, `NaN` та `Infinity`.
Для `film` і `hall` — порожні рядки й рядки з пробілів.
Для `start` — неправильний тип та дата з часовою зоною.
Тести перевіряють не тільки створення об'єкта, а й зміну властивостей після створення.

## 4. Спеціальні методи й детерміноване впорядкування

### 4.1. `__str__`

Метод `__str__` повертає коротке читабельне подання сеансу.
Воно корисне для повідомлень користувачу, журналів та діагностики.
У ньому відображаються назва фільму, зал і час початку.

### 4.2. `__repr__`

Метод `__repr__` формує докладне діагностичне подання з полями об'єкта.
Воно дає змогу зрозуміти стан екземпляра під час налагодження і при падінні тестів.

### 4.3. `__eq__`

Рівність визначається за типом об'єкта та всіма п'ятьма основними полями.
Два екземпляри одного підтипу з однаковими значеннями порівнюються як рівні.
Об'єкти різних підтипів не прирівнюються автоматично навіть за однакових полів, адже мають різну поведінку `revenue()`.
Для несумісного типу повертається `NotImplemented`, щоб Python міг застосувати правила порівняння іншого операнда.

### 4.4. Хешування

Оскільки об'єкт змінний і має власний `__eq__`, його не слід використовувати як стабільний ключ словника за значенням полів.
У класі визначено `__hash__ = None`.
Це запобігає помилкам, які виникли б після зміни поля вже захешованого об'єкта.

### 4.5. Ключ сортування

Замість перевантаження всіх операторів порівняння використовується метод `sort_key()`.
Він повертає кортеж:

```python
(self.sold, self.film, self.hall, self.start)
```

Це забезпечує зрозумілий порядок за кількістю продажів, назвою, залом і часом.
Кортеж можна передати до `sorted(..., key=...)` або `max(..., key=...)`.
Такий підхід краще за `__lt__`, якщо для різних задач можуть знадобитися різні способи впорядкування.

## 5. Успадкування, підтипи та поліморфізм

### 5.1. Ієрархія

```text
Screening
├── RegularScreening
└── PremiumScreening
```

Обидва підтипи успадковують поля, властивості, інваріанти та спеціальні методи базового класу.
Вони відрізняються реалізацією спільної операції `revenue()`.

### 5.2. Звичайний сеанс

`RegularScreening.revenue()` обчислює:

```text
revenue = price × sold
```

Наприклад, за ціни `180.00` грн і 120 проданих квитків:

```text
180.00 × 120 = 21 600.00 грн
```

### 5.3. Преміальний сеанс

`PremiumScreening.revenue()` використовує коефіцієнт `1.50`:

```text
revenue = price × sold × 1.50
```

Наприклад, за ціни `200.00` грн і 60 квитків:

```text
200.00 × 60 × 1.50 = 18 000.00 грн
```

Коефіцієнт є навчальним правилом реалізації підтипу; він не змінює історичний CSV ЛР №6.

### 5.4. Поліморфний виклик

У модулі аналізу для будь-якого сеансу виконується:

```python
income = screening.revenue()
```

Python сам визначає, реалізацію якого підтипу слід викликати.
Функції аналізу не містять ланцюжків `if isinstance(screening, RegularScreening)` / `elif ...` для вибору формули.
Це відповідає вимозі методичних вказівок не розгалужувати кожен звіт за конкретними класами.

### 5.5. `super()` і MRO

У поточній ієрархії підтипи використовують успадковану ініціалізацію базового класу без власного конструктора.
Якщо підтип визначить власний `__init__`, виклик `super().__init__(...)` дозволить повторно використати базову перевірку полів.
MRO (`Method Resolution Order`) визначає порядок пошуку методів у ланцюгу успадкування.
Для `PremiumScreening` спочатку перевіряється сам підтип, а потім `Screening`.
Саме тому перевизначений `revenue()` має пріоритет над базовим методом.

## 6. Спільний контракт `ScreeningLike(Protocol)` — завдання із зірочкою

### 6.1. Навіщо потрібен протокол

Протокол описує можливості об'єкта, які потрібні функції, не вимагаючи успадкування від конкретного класу.
У `src/kzp_lab06/protocols.py` визначено `ScreeningLike` із властивостями `film`, `hall`, `start`, `price`, `sold` та методом `revenue() -> Decimal`.

### 6.2. Структурна типізація

Функція аналізу може приймати будь-який об'єкт, що має потрібні атрибути й методи.
Це називається качиною типізацією: важлива поведінка, а не назва класу.
`RegularScreening` і `PremiumScreening` відповідають контракту завдяки своїм властивостям і методу доходу.

### 6.3. Незалежна реалізація

У тестах створено незалежний клас із потрібними полями та `revenue()`, який не успадковує `Screening`.
Він також відповідає протоколу.
Натомість звичайний `object()` без методу доходу протоколу не відповідає.
Це демонструє, що спільний інтерфейс не прив'язаний до ієрархії.

### 6.4. `@runtime_checkable`

Декоратор дозволяє виконати обмежену перевірку відповідності протоколу через `isinstance` під час виконання.
Така перевірка не доводить повної відповідності всіх анотацій типів і не замінює поведінкові тести.
Основне призначення `Protocol` — зрозумілий структурний контракт для аналізу й статичної перевірки.

## 7. Незмінні підсумки `@dataclass(frozen=True)`

### 7.1. Підсумкова модель

Модуль `analysis.py` використовує `AnalysisResult`, оформлений через `@dataclass(frozen=True)`.
Модель об'єднує результати аналізу в одному значенні.

Поля включають:

- `selected` — відібрані сеанси;
- `revenue_by_hall` — дохід за кожним залом;
- `unique_films` — множину унікальних фільмів;
- `total_revenue` — загальний дохід;
- `most_popular` — найпопулярніший сеанс або відсутність такого.

Для потокового аналізу використовується окремий підсумковий тип `StreamingAnalysisResult`, також frozen dataclass.

### 7.2. Чому `frozen=True`

Результат аналізу — підсумкове значення, яке не повинно випадково переприсвоюватися після обчислення.
`frozen=True` блокує зміну атрибутів екземпляра й підкреслює цю домовленість.

### 7.3. Межа незмінності

Заморожування dataclass є поверхневим.
Якщо поле містить список, словник або множину, вміст цієї колекції теоретично може змінюватися, хоча переприсвоїти саме поле не можна.
У звіті це зазначено окремо, щоб не стверджувати помилково про глибоку незмінність.

### 7.4. Перевірки

Тести перевіряють, що спроба переприсвоїти поле `total_revenue` спричиняє `FrozenInstanceError`.
Перевірки виконуються як для звичайного, так і для потокового результату.

## 9. Завантаження CSV і контроль помилок

### 9.1. Вхідні поля

```csv
film,hall,start,price,sold
```

Усі поля обов'язкові.
Підтримуються українські відповідники назв, що застосовувалися в Java-експорті.
Порядок стовпців визначається за заголовками, а не за фіксованими позиціями.

### 9.2. Читання

Для читання використовується `csv.DictReader`.
Файл відкривається з кодуванням `utf-8-sig` і `newline=""`.
Це дозволяє коректно обробляти CSV з UTF-8 BOM, лапками та комами всередині значень.

### 9.3. Перетворення типів

Текстове значення `start` перетворюється через `datetime.fromisoformat()`.
Ціна перетворюється на `Decimal`, а кількість продажів — на `int`.
Перевіряється відсутність часової зони, скінченність і невід'ємність ціни, невід'ємність продажів.

### 9.4. Створення об'єктів

Після успішного парсингу рядка `loader.py` створює `RegularScreening`.
Це дозволяє не змінювати історичний CSV, який не містить поля з типом сеансу.
Преміальні сеанси представлені об'єктами в тестових наборах і обробляються тими самими функціями аналізу.

### 9.5. Повідомлення про помилки

Власний виняток `DataError` повідомляє про проблеми структури або значень CSV.
Для помилки в рядку даних указується його номер, а за можливості — назва поля.
Перевіряються порожній файл, відсутній файл, неправильна кількість стовпців, некоректна дата, ціна й кількість продажів.

### 9.6. Контрольний помилковий рядок

У тестах помилка навмисно розміщується в третьому рядку CSV.
Перевіряється, що повідомлення містить саме номер рядка `3`, а не загальний текст без контексту.
Це відповідає інженерній вимозі методичних вказівок.

### 9.7. Порожній вхід

Потрібно розрізняти файл із коректним заголовком і нульовою кількістю записів та повністю порожній файл.
Перший випадок є допустимим порожнім набором сеансів.
Другий не має заголовка й призводить до `DataError`.

## 10. Алгоритм аналізу та детермінованість

### 10.1. Відбір

Відбір виконується за правилом:

```python
screening.sold > threshold
```

Поріг `50` означає, що сеанс із рівно 50 продажами не включається.
Сеанс із 51 продажем включається.

### 10.2. Агрегація доходів

Для кожного відібраного сеансу викликається `screening.revenue()`.
Результат додається до суми відповідного залу.
Загальний дохід є сумою доходів усіх відібраних сеансів.
Тип `Decimal` використовується протягом усіх фінансових обчислень.

### 10.3. Унікальні фільми

Назви фільмів збираються у множину `set`.
Це автоматично усуває повторення, але не визначає порядок виведення.
Тому для текстового звіту назви впорядковуються окремо.

### 10.4. Найпопулярніший сеанс

Основним критерієм є кількість проданих квитків.
Для однозначності при рівності продажів застосовується додатковий ключ, що враховує назву фільму, зал і час.
Це забезпечує повторюваність результатів.

### 10.5. Дублікати

Два однакові записи в CSV — це два записи даних, тому їхні доходи враховуються двічі.
Водночас назва фільму залишається єдиним елементом множини унікальних назв.
Така поведінка зафіксована тестами.

### 10.6. Потоковий аналіз

Збережено можливість послідовного читання через генератор `iter_screenings()` і потокового підсумовування.
Потоковий результат не зберігає повного списку сеансів, тому має інший профіль пам'яті.
Поліморфний виклик `revenue()` застосовується також у потоковому варіанті.

## 11. Власний контекстний менеджер — завдання із зірочкою

### 11.1. Призначення `SafeReportFile`

У модулі `report_context.py` створено клас `SafeReportFile`.
Він підтримує режими читання `"r"` і запису `"w"` та реалізує методи `__enter__` і `__exit__`.

### 11.2. Відкриття файлу

У `__enter__` файл відкривається через `pathlib.Path.open()` із кодуванням UTF-8.
Для запису використовується завершення рядків `LF`.
Це робить новий звіт відтворюваним на різних платформах.

### 11.3. Закриття файлу

Метод `__exit__` закриває файловий об'єкт незалежно від того, чи завершився блок `with` успішно, чи було викинуто виняток.
Метод повертає `False`, тому виняток не приховується від виклику.

### 11.4. Інтеграція

Функція `save_report()` у `reporting.py` використовує цей менеджер для запису текстового звіту.
Отже, зірочкове завдання не залишилося ізольованим демонстраційним прикладом, а включене до реального шляху збереження результатів.

### 11.5. Тестування

Створено тести на запис і читання UTF-8, коректне закриття після нормального виходу, закриття під час винятку й відхилення неправильного режиму.
Перевірка закриття під час винятку є окремою вимогою методичних вказівок.

### 12.1. Кількість записів

Методичні вказівки вимагають не менше шести записів, наявності обох підтипів, дублювання, граничного setter, помилкового CSV і порожнього входу.

Тести `test_analysis_polymorphism.py` використовують сім об'єктів обох підтипів.

Для об'єктів різних підтипів з однаковими полями перевіряється відмінність.

## 22. Відповіді на 20 контрольних питань ЛР №7

### 22.1. Чим клас відрізняється від екземпляра?

Клас є описом структури та поведінки об'єктів, а екземпляр — конкретним об'єктом із власними значеннями полів.
`Screening` описує, що має кіносеанс, тоді як створений `RegularScreening("Дюна", ...)` містить конкретні дані про певний показ.

### 22.2. Яку роль виконує `__init__` і що означає `self`?

`__init__` ініціалізує стан нового екземпляра.
`self` — посилання на об'єкт, для якого викликається метод.
У `Screening.__init__` присвоєння через `self.price` і `self.sold` запускає перевірку властивостей.

### 22.3. Для чого застосовується `@property`?

`@property` дозволяє надати полю зручний зовнішній інтерфейс, залишивши контроль за його читанням і зміною.
Це допомагає забезпечити інваріанти: наприклад, кількість продажів не може бути від'ємною.

### 22.4. Чому setter записує у внутрішнє поле, а не у властивість?

Якщо setter виконає `self.sold = value`, він знову викличе сам себе й спричинить рекурсію.
Присвоєння `self._sold = value` змінює внутрішнє поле без повторного виклику setter.

### 22.5. Яку поведінку автоматично додає `@dataclass`?

`@dataclass` може автоматично створити конструктор, текстове подання, порівняння та інші службові методи на основі оголошених полів.
У цьому проєкті він зручний для підсумків аналізу, а не для сутності зі складною setter-логікою.

### 22.6. Навіщо застосовується `frozen=True`?

`frozen=True` забороняє звичайне переприсвоєння полів dataclass після створення.
Це захищає підсумок від випадкових змін, хоча не заморожує вкладені списки, словники й множини автоматично.

### 22.7. Чим відрізняються `__str__` і `__repr__`?

`__str__` орієнтований на читабельне представлення для користувача.
`__repr__` призначений переважно для налагодження й повинен показувати достатньо деталей про стан об'єкта.

### 22.8. Як `__eq__` має поводитися з несумісним типом?

Якщо інший об'єкт має несумісний тип, коректно повернути `NotImplemented`, а не примусово порівнювати випадкові поля.
Python тоді може спробувати зворотне порівняння іншого операнда або визначити нерівність.

### 22.9. Коли сортування через `key` краще за реалізацію `__lt__`?

`key` краще, коли потрібне конкретне впорядкування для окремої задачі й немає єдиного природного порядку всіх об'єктів.
Для сеансів можна сортувати за продажами, назвою, залом і часом, не нав'язуючи цей порядок усім операторам порівняння.

### 22.10. Яку роль виконує `super()`?

`super()` забезпечує доступ до наступної реалізації методу за порядком пошуку методів.
У конструкторі підтипу його можна використати для виклику базової ініціалізації та повторного застосування перевірок полів.

### 22.11. Що таке MRO і чому його потрібно враховувати?

MRO — порядок пошуку методів у класі та його предках.
Він визначає, який метод буде викликано, особливо за перевизначення або множинного успадкування.
У `PremiumScreening` метод `revenue()` самого підтипу має пріоритет над реалізацією базового класу.

### 22.12. Що означає качина типізація?

Качина типізація означає використання об'єкта за його доступною поведінкою, а не за обов'язковою належністю до конкретного класу.
Якщо об'єкт має поля сеансу та метод `revenue()`, його можна передати до функції, що очікує цей інтерфейс.

### 22.13. Яку проблему розв'язує `Protocol`?

`Protocol` формально описує структурний контракт, зменшуючи залежність функцій від конкретної ієрархії класів.
`ScreeningLike` дозволяє аналізувати як штатні підтипи, так і незалежні об'єкти з потрібним набором властивостей і методів.

### 22.14. Чому `analysis` не повинен перевіряти кожен конкретний підтип?

Такі перевірки створили б жорстку залежність від усіх наявних класів.
Поліморфний виклик `screening.revenue()` дозволяє додати новий підтип без переписування логіки агрегування доходів.

### 22.15. Де має виконуватися перетворення словника на об'єкт?

У модулі завантаження `loader.py`, одразу після читання й перевірки CSV-рядка.
Тоді інші модулі працюють із перевіреними об'єктами й не повторюють перетворення текстових значень.

### 22.16. Чому модулі не повинні запускати CLI під час імпорту?

Імпорт повинен надавати класи й функції без побічних ефектів, таких як читання файлів, друк або завершення процесу.
Це робить модулі придатними для тестування, повторного використання й інтеграції з іншими програмами.

### 22.17. Які властивості об'єктів перевіряються тестами?

Перевіряються допустимі й недопустимі значення полів, зміни через setter, рівність, текстові подання, сортування, різні формули доходу та відповідність спільному протоколу.
Окремо перевіряється незмінність підсумкового dataclass.

### 22.18. Для чого потрібні pytest, Ruff і wheel?

`pytest` перевіряє поведінку програми автоматизованими тестами.
`Ruff` контролює вибрані правила якості коду та форматування.
`wheel` є стандартним форматом Python-дистрибутива, який можна встановити в окреме середовище й перевірити незалежно від робочого дерева.

### 22.19. Які крайові випадки має містити тестовий набір?

Нульові та від'ємні значення, неправильні типи, порожні назви, дублікати, рівні значення ключів сортування, порожній CSV, відсутній файл, неправильну кількість стовпців, невалідні дати й ціни, обидва підтипи, помилки CLI та виняток усередині `with`.
Для варіанта 19 особливо важливо перевірити межу `sold > threshold`.

## 3. Формат вхідного CSV-файлу

Відповідно до завдання використовується CSV із заголовком:

```csv
film,hall,start,price,sold
```

Призначення стовпців:

| Стовпець | Тип Python | Опис |
|---|---|---|
| `film` | `str` | Назва фільму |
| `hall` | `str` | Ідентифікатор залу |
| `start` | `datetime` | Дата й час сеансу |
| `price` | `Decimal` | Ціна одного квитка |
| `sold` | `int` | Кількість проданих квитків |

Приклад:

```csv
film,hall,start,price,sold
Avatar,2,2026-10-20T18:00,150.0,100
Dune,1,2026-10-20T20:00,200.0,80
Interstellar,3,2026-10-21T16:30,180.0,120
```

Програма підтримує також україномовні назви стовпців Java-експорту:

```csv
фільм,зал,продано,час,ціна
```

Порядок стовпців може відрізнятися, оскільки значення отримуються за назвами полів через `csv.DictReader`.

Для правильного оброблення назв фільмів, що містять кому, використовується стандартне CSV-екранування:

```csv
"Spider-Man, No Way Home",1,2026-10-22T18:00,170.0,75
```

Порожній CSV, який містить лише заголовок, обробляється як порожній набір сеансів. Некоректна структура файлу або значення призводять до контрольованої помилки.

Файли відкриваються з параметром `newline=""`, щоб модуль `csv` самостійно обробляв завершення рядків. Кодування `utf-8-sig` дозволяє читати UTF-8-файли з маркером BOM.

## 5. Перетворення типів, колекції та comprehensions

Після читання CSV усі значення спочатку є текстовими.

Для подальшого аналізу виконуються перетворення:

```python
datetime.fromisoformat(value)
Decimal(value)
int(value)
```

Тип `Decimal` використано для ціни, оскільки він забезпечує точні десяткові обчислення та дозволяє уникнути характерних для `float` похибок представлення грошових значень.

У проєкті використовуються три основні колекції:

**Список (`list`)** — зберігає послідовність кіносеансів і результати фільтрації.

**Словник (`dict`)** — пов'язує ідентифікатор залу з його сумарним доходом.

**Множина (`set`)** — зберігає унікальні назви фільмів без повторень.

Для відбору сеансів застосовано list comprehension:

```python
selected = [screening for screening in screenings if screening.sold > threshold]
```

Для визначення унікальних фільмів використано set comprehension:

```python
unique_films = {screening.film for screening in selected}
```

Таким чином, реалізовано щонайменше два різновиди comprehension.

## 6. Функції з параметрами за замовчуванням, *args та **kwargs

У модулі `utils.py` реалізовано функцію `describe_screening()`.

Її сигнатура:

```python
def describe_screening(
    film: str = "Невідомий",
    *args: str,
    **kwargs: object,
) -> str:
```

У цій функції:

- `film` — параметр зі значенням за замовчуванням;
- `*args` — додаткові позиційні аргументи;
- `**kwargs` — додаткові іменовані аргументи.

Завдяки такій сигнатурі функцію можна викликати з різною кількістю додаткових характеристик сеансу.

Для функції написано чотири тести, що перевіряють використання параметра за замовчуванням, позиційних аргументів, іменованих аргументів та їхньої комбінації.

## 7. Фільтрація, агрегація та детермінованість

### Фільтрація сеансів

Користувач задає поріг продажів через `--threshold`.

За замовчуванням:

```python
threshold = 50
```

Умова відбору:

```python
screening.sold > threshold
```

Отже, при порогу 50 сеанс із 50 продажами не проходить фільтр, а сеанс із 51 продажем проходить.

### Обчислення доходу

Для кожного сеансу:

```python
revenue = screening.price * screening.sold
```

Дохід кожного залу дорівнює сумі доходів його відібраних сеансів.

Загальний дохід обчислюється підсумовуванням доходів усіх відібраних сеансів.

### Унікальні фільми

Назви фільмів збираються у множину `set`, тому повторення автоматично усуваються.

### Найпопулярніший сеанс

Найпопулярнішим визначається сеанс із найбільшою кількістю проданих квитків.

Для однозначності результату при однаковій кількості продажів використовується додаткове впорядкування за назвою фільму, залом і часом.

### Детермінованість звіту

Під час формування звіту дані, для яких порядок має значення, виводяться у визначеному порядку. Це забезпечує повторюваність результатів та спрощує автоматизоване тестування.

## 8. Оброблення помилок

Для перевірки даних використовується власний клас `DataError`.

Перевіряються:

1. Відсутність обов'язкових стовпців.
2. Неоднозначність назв стовпців.
3. Неправильна кількість полів у CSV-рядку.
4. Порожні обов'язкові значення.
5. Некоректний формат дати.
6. Некоректна ціна.
7. Від'ємна ціна.
8. Некоректна кількість продажів.
9. Від'ємна кількість продажів.
10. Помилки відкриття та читання файлу.

Для збереження першопричини помилки використовується механізм:

```python
raise DataError(...) from error
```

Він дозволяє пов'язати зрозуміле повідомлення про помилку вхідних даних із початковим винятком Python.

Консольний інтерфейс повертає:

- `0` — успішне завершення;
- `2` — очікувана помилка оброблення даних або роботи з файлом.

Це дозволяє автоматизованим системам визначати результат виконання програми.

### Приклад результатів аналізу Java-експорту

## 15. Відповіді на контрольні запитання

### 1. Яку роль виконує pyproject.toml у Python-проєкті?

`pyproject.toml` є центральним конфігураційним файлом сучасного Python-проєкту. Він містить метадані пакета, вимоги до Python, налаштування системи збирання, залежності та конфігурацію інструментів, зокрема pytest і Ruff.

### 2. Навіщо створюється віртуальне середовище?

Віртуальне середовище ізолює залежності конкретного проєкту від глобально встановлених пакетів Python. Це допомагає уникати конфліктів версій та забезпечує відтворюваність середовища розробки.

### 3. Чому CSV-файл відкривається з newline=""?

Параметр `newline=""` передає керування обробленням завершень рядків модулю `csv`. Це особливо важливо для коректного читання CSV, у якому поля можуть містити перенесення рядків.

### 4. Які типи повертає csv.DictReader без додаткового перетворення?

`csv.DictReader` повертає записи у вигляді словників. Зазвичай ключами є рядкові назви стовпців, а значеннями — рядки. Числа й дати необхідно перетворювати окремо.

### 5. Чому split(",") не є коректним CSV-парсером?

Метод `split(",")` розділяє рядок за кожною комою, не враховуючи лапки та правила екранування CSV. Наприклад, назва фільму `"Spider-Man, No Way Home"` містить кому, але повинна залишатися одним полем.

### 6. Як відрізняються список, словник і множина?

Список зберігає впорядковану послідовність елементів і допускає повторення. Словник зберігає пари «ключ — значення». Множина зберігає унікальні елементи та зручна для усунення повторів.

### 7. Коли comprehension робить код зрозумілішим, а коли краще використати цикл?

Comprehension зручний для коротких операцій фільтрації або перетворення колекцій. Звичайний цикл краще використовувати, якщо оброблення містить складну логіку, кілька умов, обробку помилок або побічні ефекти.

### 8. Що містять *args і **kwargs усередині функції?

`*args` збирає додаткові позиційні аргументи в кортеж. `**kwargs` збирає додаткові іменовані аргументи у словник.

### 9. Чому змінний об'єкт небезпечний як значення за замовчуванням?

Значення за замовчуванням створюється під час визначення функції. Якщо це змінний об'єкт, наприклад список, його зміни можуть зберігатися між викликами функції. Зазвичай для таких випадків використовують `None` і створюють новий об'єкт усередині функції.

### 10. Як raise ... from error зберігає першопричину?

Конструкція `raise ... from error` створює явний зв'язок між новим винятком і початковою помилкою. Завдяки цьому під час налагодження можна побачити не лише зрозуміле повідомлення, а й технічну причину збою.

### 11. Чому завантаження, аналіз і запис звіту розділяються на модулі?

Розділення відповідальності спрощує розробку, тестування та супровід. Кожен модуль виконує окреме завдання, тому зміни формату звіту не повинні впливати на логіку читання CSV або аналізу даних.

### 12. Яку гарантію дає with під час роботи з файлом?

Конструкція `with` забезпечує виклик механізму завершення роботи контекстного менеджера після виходу з блоку, зокрема в разі винятку. Для файлового об'єкта це означає коректне закриття файлу.

### 13. Чому звіт має формуватися в детермінованому порядку?

Детермінований порядок забезпечує однаковий результат для однакових вхідних даних. Це спрощує порівняння звітів, автоматизоване тестування та пошук помилок.

### 14. Які випадки повинні бути перевірені для порожнього CSV?

Потрібно розрізняти файл із коректним заголовком, але без записів, і файл без необхідного заголовка. Перший випадок може означати порожній набір даних, а другий — помилку формату. Також важливо перевірити поведінку аналізу та звіту для порожньої вибірки.

### 15. Чим тест поведінки відрізняється від перевірки внутрішньої реалізації?

Тест поведінки перевіряє результат роботи функції для заданих умов. Тест внутрішньої реалізації залежить від конкретного способу написання коду. Поведінкові тести зазвичай стійкіші до рефакторингу.

### 16. Які файли знаходить pytest?

За типовими правилами pytest шукає файли `test_*.py` та `*_test.py`, а всередині них — тестові функції й методи за відповідними правилами іменування. У цьому проєкті пошук тестів налаштовано на папку `tests`.

### 17. Які перевірки виконує Ruff?

Ruff виконує статичний аналіз Python-коду, виявляючи порушення вибраних правил, наприклад зайві імпорти та проблеми стилю. Ruff також має окремий інструмент форматування, який перевіряє або змінює оформлення коду.

### 18. Які коди завершення має CLI для успіху та очікуваної помилки?

У реалізованій програмі код `0` означає успішне виконання, а код `2` — очікувану помилку даних або роботи з файлом. Це дозволяє іншим програмам і CI визначати результат запуску.

### 19. Чому в CI запускаються і тести, і аналізатор, і пакетування?

Ці перевірки контролюють різні аспекти якості. Тести перевіряють поведінку програми, Ruff — якість і форматування коду, а пакетування — можливість створити встановлюваний дистрибутив. Разом вони забезпечують ширшу перевірку проєкту.

### 20. Які дані та результати потрібно задекларувати в REPORT?

У звіті необхідно зазначити тему, варіант, середовище розробки, формат вхідних даних, архітектуру, основні алгоритми, оброблення помилок, приклади результатів, тести, перевірки Ruff, пакетування, CI, GitHub Issues та Pull Request, використання ШІ, додаткові завдання й підсумковий висновок.

Налаштовано GitHub Actions для автоматичної перевірки на Windows, Ubuntu та macOS. Під час тестування було виявлено проблему кодування українського тексту в середовищі Windows CI. Після її виправлення всі три операційні системи успішно пройшли перевірки.

У межах додаткового завдання реалізовано потокове читання CSV через генератор. Експериментальне порівняння показало суттєве зменшення пікового використання пам'яті під час послідовного читання великих наборів даних.

Таким чином, мету лабораторної роботи досягнуто. Отримано практичний досвід розроблення Python-застосунків, роботи з CSV, модульного проєктування, оброблення винятків, автоматизованого тестування, пакетування, налаштування CI та організації розробки через GitHub.
