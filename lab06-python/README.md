## 6. Формат вхідного CSV

### 6.1. Заголовок

```csv
film,hall,start,price,sold
```

| Поле | Тип після перетворення | Правило |
|---|---|---|
| `film` | `str` | Непорожня назва |
| `hall` | `str` | Непорожній ідентифікатор |
| `start` | `datetime` | Коректна дата і час без часової зони |
| `price` | `Decimal` | Скінченне невід'ємне число |
| `sold` | `int` | Невід'ємне ціле число |

### 6.2. Контрольний набір даних

Контрольний файл `data/input.csv` містить сім записів, тобто перевищує мінімум шість із методичних вказівок.

```csv
film,hall,start,price,sold
Інтерстеллар,1,2026-11-02T18:00,180.00,120
Дюна,2,2026-11-02T19:30,200.00,85
Аватар,3,2026-11-03T17:00,220.00,150
Інтерстеллар,2,2026-11-03T20:00,180.00,100
"Місія, нездійсненна",1,2026-11-04T16:30,190.00,50
Оппенгеймер,3,2026-11-04T21:00,210.00,0
Дюна,1,2026-11-05T18:30,200.00,75
```

Цей CSV навмисно залишено у форматі попередньої роботи.
У ньому немає додаткового стовпця типу сеансу.
Тому поточний loader створює `RegularScreening` для кожного запису.
Преміальні об'єкти створюються окремо у тестах поліморфізму.

### 6.3. Чому використовується csv.DictReader

Модуль `csv` коректно обробляє коми всередині лапок, порядок стовпців і спеціальні символи.
Застосування `split(",")` пошкодило б назву `"Місія, нездійсненна"`.
Завантажувач визначає потрібні значення за назвами стовпців, а не за їхніми позиціями.

### 6.4. Кодування

Файл читається у кодуванні `utf-8-sig`.
Це дозволяє приймати як звичайний UTF-8, так і CSV із маркером BOM.
Параметр `newline=""` залишає обробку завершень рядків стандартному модулю `csv`.

## 7. Базовий клас Screening

### 7.1. Призначення

`Screening` — базова предметна сутність, що представляє один кіносеанс.
Вона об'єднує стан, перевірки та операцію обчислення доходу.

Конструктор приймає п'ять значень:

```python
Screening(
    film: str,
    hall: str,
    start: datetime,
    price: Decimal,
    sold: int,
)
```

### 7.2. Інкапсуляція

Зовнішній код звертається до полів як до звичайних атрибутів.
Однак читання та запис проходять через властивості, визначені декоратором `@property`.
Внутрішні поля з підкресленням використовуються для збереження перевіреного стану.

Перевага цього підходу полягає у збереженні інваріантів після створення об'єкта.
Якщо кількість продажів змінюється, нове значення перевіряється повторно.
Отже, перевірка не обмежується лише початковим читанням CSV.

### 7.3. Перевірка назви фільму

Поле `film` повинно бути рядком із непорожнім вмістом.
Порожній рядок або рядок лише з пробілами відхиляється.
Такий об'єкт не має достатньої інформації для коректного звіту.

### 7.4. Перевірка залу

Поле `hall` також повинно містити непорожній рядок.
Ідентифікатор залу зберігається текстом, як і в попередній лабораторній.
Це не вимагає штучного перетворення номерів залів на цілі числа.

### 7.5. Перевірка часу

Поле `start` має бути екземпляром `datetime`.
У поточній моделі не використовуються значення з часовою зоною.
Некоректні дати відхиляються на етапі завантаження CSV.

### 7.6. Перевірка ціни

Поле `price` зберігається як `Decimal`.
Допустимі значення — скінченні числа від нуля включно.
Від'ємні ціни, `NaN` і нескінченність відхиляються.

Нульова ціна допустима як граничне значення.
Це дозволяє коректно моделювати безоплатний показ без порушення правил типізації.

### 7.7. Перевірка продажів

Поле `sold` повинно бути цілим невід'ємним числом.
Нуль продажів є коректним випадком.
Від'ємне значення відхиляється.
Логічні значення `True` і `False` не приймаються замість цілих чисел.

## 8. Успадкування та підтипи

### 8.1. RegularScreening

`RegularScreening` успадковує спільні поля та правила базового класу.
Його формула доходу є звичайним добутком ціни на кількість проданих квитків.

\[
\text{revenue}_{regular} = \text{price} \times \text{sold}
\]

Наприклад, за ціни `200.00` грн і 80 продажів дохід становить `16000.00` грн.

### 8.2. PremiumScreening

`PremiumScreening` представляє преміальний сеанс.
Він використовує той самий інтерфейс `revenue()`, але іншу формулу.

\[
\text{revenue}_{premium} = \text{price} \times \text{sold} \times 1.50
\]

Множник `1.50` у поточній реалізації є константою `PREMIUM_MULTIPLIER`.
Він задає навчальну відмінність між двома типами сеансів.
Це не зовнішній тариф кінотеатру, а правило предметної моделі ЛР №7.

### 8.3. Приклад поліморфізму

```python
from datetime import datetime
from decimal import Decimal
from kzp_lab06.models import PremiumScreening, RegularScreening

regular = RegularScreening("Дюна", "1", datetime(2026, 11, 5, 18), Decimal("200"), 80)
premium = PremiumScreening("Дюна", "2", datetime(2026, 11, 5, 20), Decimal("200"), 80)

assert regular.revenue() == Decimal("16000")
assert premium.revenue() == Decimal("24000.00")
```

Обидва об'єкти підтримують один і той самий метод.
Код аналізу не повинен перевіряти, який саме підтип передано.
Python сам вибирає відповідну реалізацію методу під час виконання.

## 9. Спеціальні методи Python

### 9.1. __str__

`__str__` формує читабельне представлення кіносеансу.
Його призначення — повідомлення для людини, а не серіалізація даних.

### 9.2. __repr__

`__repr__` містить назву класу та значення полів.
Він корисний під час налагодження й аналізу невдалих тестів.

### 9.3. __eq__

`__eq__` порівнює значення полів двох об'єктів сумісного типу.
У цій реалізації порівняння також враховує точний клас об'єкта.
Два однакові `RegularScreening` можуть бути рівними за значенням.
Але `RegularScreening` та `PremiumScreening` не вважаються рівними лише через однакові поля.

Для несумісного типу метод повертає `NotImplemented`.
Це дозволяє Python застосувати стандартний механізм порівняння.

### 9.4. Змінюваність і хешування

Стан `Screening` може змінюватися через сетери.
Тому клас не призначено для використання як незмінного ключа словника.
У реалізації хешування вимкнено за допомогою `__hash__ = None`.

### 9.5. sort_key

Метод `sort_key()` повертає ключ із кількості продажів, назви фільму, залу та часу.
Такий підхід дозволяє отримувати повторюваний порядок без реалізації всіх операторів порівняння.
Детермінованість особливо важлива для тестів і порівняння звітів.

## 10. Незмінні підсумки через dataclass

Модуль аналізу використовує `AnalysisResult` з декоратором `@dataclass(frozen=True)`.
Окремо для потокового аналізу існує `StreamingAnalysisResult`.

До результатів належать:

- список відібраних сеансів або їхня кількість;
- дохід за кожним залом;
- множина унікальних назв фільмів;
- загальний дохід;
- найпопулярніший сеанс.

Перевага `dataclass` — стислий опис структурованого підсумку.
`frozen=True` забороняє повторне присвоєння полів результату.
Тести перевіряють цю поведінку через `FrozenInstanceError`.

Водночас заморожування є **неглибоким**.
Якщо поле містить звичайний список, словник або множину, їхній вміст сам по собі не стає незмінним.
Це обмеження важливо враховувати під час подальшого розвитку програми.

## 11. Завдання із зірочкою: Protocol

### 11.1. Призначення

У файлі `protocols.py` оголошено `ScreeningLike` на основі `typing.Protocol`.
Протокол описує не походження об'єкта, а його необхідні можливості.

Контракт включає:

- властивість `film`;
- властивість `hall`;
- властивість `start`;
- властивість `price`;
- властивість `sold`;
- метод `revenue() -> Decimal`.

### 11.2. Структурна типізація

Об'єкт може відповідати протоколу навіть без успадкування від `Screening`.
Головне — наявність потрібних атрибутів і методу з відповідним контрактом.
Це приклад структурної типізації та принципу «качиного» типування.

### 11.3. Використання в аналізі

Функції аналізу приймають об'єкти через спільний інтерфейс.
Вони звертаються до `screening.revenue()`, а не до формули конкретного підтипу.
Це полегшує додавання нових видів кіносеансів.

### 11.4. Перевірки протоколу

У `test_protocols.py` перевіряються обидва підтипи.
Також перевіряється сторонній об'єкт із потрібними властивостями й методом.
Окремий тест показує, що об'єкт без `revenue()` не задовольняє контракту.

## 12. Завдання із зірочкою: власний контекстний менеджер

### 12.1. Призначення SafeReportFile

У `report_context.py` реалізовано `SafeReportFile`.
Цей клас керує життєвим циклом файлового об'єкта під час читання або запису звіту.

### 12.2. Метод __enter__

`__enter__` відкриває файл за вказаним шляхом і повертає файловий об'єкт.
Для текстових даних використовується кодування UTF-8.
Під час запису застосовуються завершення рядків `LF`.

### 12.3. Метод __exit__

`__exit__` закриває відкритий файл після завершення блоку `with`.
Закриття відбувається також тоді, коли всередині блоку виникає виняток.
Метод повертає `False`, тому не приховує помилку від викликаючого коду.

### 12.4. Приклад використання

```python
from kzp_lab06.report_context import SafeReportFile

with SafeReportFile("reports/example.txt", "w") as report:
    report.write("Звіт кінотеатру\n")
```

### 12.5. Тести безпечного завершення

У `test_report_context.py` перевірено читання, запис і кодування UTF-8.
Окремо перевірено поведінку за некоректного режиму.
Ключовий тест навмисно викликає виняток усередині `with`.
Після цього перевіряється, що файл закрито, а виняток не втрачено.

## 13. Завантаження CSV і створення об'єктів

### 13.1. iter_screenings

`iter_screenings(path)` читає CSV поступово та повертає об'єкти сеансів.
Функція не повинна передавати до аналізу рядки з некоректними значеннями.

### 13.2. load_screenings

`load_screenings(path)` перетворює генератор на список об'єктів.
Це зручно для звичайного аналізу, який зберігає відібрані записи у підсумку.

### 13.3. Перетворення типів

Для часу використовується `datetime.fromisoformat()`.
Для ціни використовується `Decimal()`.
Для продажів використовується `int()`.
Після перетворення об'єкт додатково проходить валідацію конструктора.

### 13.4. Помилки CSV

Виняток `DataError` надає зрозуміле повідомлення про проблему.
Для некоректного рядка повідомлення може містити його номер і назву поля.
Це дозволяє виправити вхідний файл без перегляду всієї реалізації.

Перевіряються такі випадки:

1. Відсутній CSV-файл.
2. Порожній файл без заголовка.
3. Відсутній обов'язковий стовпець.
4. Дублювання або неоднозначність назв стовпців.
5. Надмірна кількість полів у рядку.
6. Недостатня кількість полів у рядку.
7. Порожня назва фільму.
8. Порожній ідентифікатор залу.
9. Некоректна дата або час.
10. Час із часовою зоною.
11. Від'ємна ціна.
12. Нескінченна ціна або `NaN`.
13. Неціле значення кількості продажів.
14. Від'ємна кількість продажів.

## 14. Аналіз кіносеансів

### 14.1. Порогова фільтрація

За замовчуванням використовується поріг `50`.
До вибірки потрапляють лише сеанси, для яких `sold > 50`.
Тому 50 продажів не проходять фільтр, а 51 — проходить.

### 14.2. Доходи за залами

Для кожного відібраного об'єкта викликається `revenue()`.
Отримана сума додається до підсумку відповідного залу.
Результат зберігається у словнику, де ключем є ідентифікатор залу.

### 14.3. Загальний дохід

Загальний дохід — сума результатів `revenue()` усіх відібраних сеансів.
Для точності використовуються десяткові числа `Decimal`.

### 14.4. Унікальні фільми

Назви відібраних фільмів зберігаються у множині.
Повторний показ того самого фільму не збільшує кількість унікальних назв.

### 14.5. Найпопулярніший сеанс

Основним критерієм є кількість проданих квитків.
Додаткові поля використовуються для визначеності результату за однакових продажів.

### 14.6. Порожній набір

Порожній список сеансів не повинен спричиняти аварійне завершення аналізу.
Підсумкові суми в такому випадку дорівнюють нулю.
Найпопулярніший сеанс відсутній.

### 14.7. Дубльовані записи

Два однакові рядки CSV — це два окремі записи про продажі.
Під час підрахунку доходу вони враховуються обидва.
Водночас множина унікальних фільмів містить назву лише один раз.

## 15. Потоковий аналіз

Функціональність потокового читання, реалізована у ЛР №6, збережена.
`analyze_screenings_streaming()` дозволяє обчислювати агрегати без збереження всіх відібраних сеансів.
Цей підхід корисний для великих CSV-файлів.

Звичайний аналіз зручний, коли потрібен докладний перелік сеансів у звіті.
Потоковий аналіз зручний, коли достатньо підсумкових показників.
Обидва підходи мають правильно викликати метод `revenue()` об'єкта.

**Примітка:** вимірювання пам'яті ЛР №6 порівнювали звичайне та потокове читання.
Окреме порівняння пам'яті *словникової та об'єктної моделей* для ЛР №7 ще не зафіксовано.
Не слід подавати результати попереднього експерименту як новий вимір.

## 16. Формування текстового звіту

### 16.1. build_report

`build_report()` перетворює підсумок аналізу на текст.
Він формує розділи зі списком відібраних сеансів і статистикою продажів.

### 16.2. Детермінований порядок

Для стабільності звіту впорядковуються зали та назви унікальних фільмів.
Це дозволяє порівнювати результати різних запусків і реалізацій.

### 16.3. save_report

`save_report()` записує підготовлений текст через `SafeReportFile`.
Звіт зберігається у UTF-8.
Під час запису використовуються завершення рядків `LF`.

### 16.4. Сумісність із попереднім звітом

Для контрольного CSV порівняно результати ЛР №6 та ЛР №7.
Після нормалізації завершень рядків **текстовий вміст збігається**.
Початковий файл мав `CRLF`, а новий — `LF`.
Отже, файли не є побайтово ідентичними, хоча розрахунки та текст однакові.

## 25. Перевірка сумісності та відтворюваності

### 25.1. Один вхід — два звіти

Для коректного порівняння потрібно використовувати той самий CSV і той самий поріг.
Порівнювати звіти на різних наборах даних було б методично некоректно.

### 25.2. Вміст і байти

На Windows попередній звіт містив `CRLF`, а новий записано з `LF`.
Це змінює розмір файлу, але не зміст рядків.
Тому в перевірці розділено текстову еквівалентність і побайтову ідентичність.

### 25.3. Порівняння моделей

У словниковій моделі поле отримують за ключем, наприклад `row["sold"]`.
В об'єктній моделі звертаються до властивості `screening.sold`.
У словниковій моделі формула доходу зазвичай розташована поза записом.
В об'єктній моделі вона викликається як `screening.revenue()`.

Це полегшує розширення поведінки без зміни кожної функції аналізу.
Натомість об'єкти потребують чітко визначених класів, контрактів і тестів стану.
Докладне порівняння переваг та обмежень слід навести у звіті ЛР №7.

## 26. Межі поточної реалізації

### 26.1. Тип сеансу в CSV

Поточний формат CSV не містить окремого поля типу.
Тому loader не може визначити преміальний сеанс без додаткових правил.
Щоб зберегти сумісність, усі записи контрольного CSV завантажуються як звичайні.
Преміальна поведінка продемонстрована окремими об'єктами в тестах.

### 26.2. Заморожені результати

`frozen=True` не заморожує вкладені списки, словники й множини.
Для повної незмінності потрібні додаткові структури або копіювання.

### 26.3. Вимірювання пам'яті

Результати потокового аналізу ЛР №6 не є порівнянням словників та ООП-моделей.
Для додаткового бала з ЛР №7 необхідний окремий контрольований експеримент.

### 26.4. Віддалена перевірка

До отримання результатів GitHub Actions не можна заявляти, що CI ЛР №7 успішний.
Аналогічно Git-тег і злиття Pull Request фіксуються лише після фактичного виконання.

## 28. Підготовка до захисту

### 28.1. Клас і екземпляр

Клас задає структуру та поведінку.
Екземпляр містить конкретний стан одного кіносеансу.

### 28.2. __init__ та self

`__init__` встановлює початкові поля об'єкта.
`self` посилається на поточний екземпляр.

### 28.3. Навіщо потрібен setter

Setter підтримує інваріант після створення об'єкта.
Наприклад, не дозволяє змінити `sold` на від'ємне значення.

### 28.4. Чому не можна присвоювати властивість усередині її setter

Присвоєння `self.sold = value` всередині `sold.setter` повторно викличе той самий setter.
Тому перевірене значення записують у внутрішнє поле.

### 28.5. Навіщо потрібен dataclass

`dataclass` автоматизує типові методи простого контейнера даних.
Він зручний для підсумку, але не замінює модель із суттєвою поведінкою та сетерами.

### 28.6. Чим відрізняються str та repr

`str` орієнтований на читача.
`repr` призначений насамперед для діагностики й розробника.

### 28.7. Як працює поліморфізм

Один виклик `revenue()` дає різний результат залежно від реалізації об'єкта.
Функції аналізу не повинні дублювати ці формули.

### 28.8. Навіщо потрібен Protocol

`Protocol` описує потрібні властивості та методи без вимоги успадкування від конкретного класу.
Це зменшує зв'язаність компонентів.

### 28.9. Чому важливий контекстний менеджер

Контекстний менеджер закриває файл і за успішного завершення, і за винятку.
Власна реалізація демонструє механізм `__enter__` та `__exit__`.

### 28.10. Чому потрібні поведінкові тести

Тести перевіряють спостережуваний результат, а не лише форму вихідного коду.
Вони дозволяють змінювати реалізацію, не втрачаючи контракту програми.

### 28.11. Чому використовується Decimal

`Decimal` підтримує точне десяткове подання грошових значень.
Це важливо для відтворюваності фінансових підсумків.

### 28.12. Навіщо потрібен CI

CI автоматично запускає тести, перевірку стилю та пакетування на різних системах.
Це доповнює локальні перевірки, але не замінює аналіз результатів.

## 30. Висновок до ЛР №7

У межах лабораторної роботи №7 предметну модель кінотеатру переведено на об'єктно-орієнтований підхід.
Базовий клас `Screening` інкапсулює стан і забезпечує перевірку значень.
Підтипи `RegularScreening` та `PremiumScreening` демонструють успадкування й поліморфізм.
Підсумкові структури `dataclass(frozen=True)` відокремлено від змінюваних сутностей.
Спеціальні методи роблять об'єкти зручними для виведення, порівняння та впорядкування.

Завдання із зірочкою реалізовано через `ScreeningLike(Protocol)` і власний `SafeReportFile`.
Поведінкові тести охоплюють коректні, граничні та помилкові сценарії.
Локально підтверджено 77 успішних тестів, перевірки Ruff і створення wheel `7.0.0.1`.
Порівняння на контрольному CSV підтвердило збереження результатів попередньої роботи.

Для завершення повного циклу залишаються фінальна документація, публікація гілки, Pull Request, віддалений CI та тег.
Історичний зміст ЛР №6 залишається частиною проєкту та не потребує видалення.
